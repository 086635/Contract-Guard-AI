## 1. 项目定位与业务全貌

### 1.1 业务目标

一个面向企业的**合同智能审核与风险预警**系统：用户上传合同（DOCX / 数字版 PDF / 扫描件 / 图片），系统完成
**解析 → 分类 → 要素抽取 → 风险识别 → 标准条款比对 → 跨条款矛盾检测 → 印章签名合规 → 报告生成 → 多轮 AI 改写**。

### 1.2 赛题硬指标（这些数字决定了技术选型的下限）

| 指标 | 阈值 | 对本项目的技术含义 |
|---|---|---|
| 合同类型分类准确率 | ≥ 85% | 需要**真实语义向量 + LLM**，哈希伪向量不可能达标 |
| 关键要素抽取 F1 | ≥ 80% | 依赖 OCR / 版面解析质量 + 结构化输出约束 |
| 风险条款识别召回 / 精准 | ≥ 75% / 75% | 依赖 RAG 召回率 + 精排质量 + 10 类风险标签体系 |
| 报告含原文位置 / 等级 / 建议 / 缺失提醒 | 必须 | 依赖 **BBox 坐标闭环**（前端 PDF.js 高亮） |

### 1.3 三大创新点（也是本项目的评分差异化来源）

1. **多轮对话修改**（rewrite Agent + 分层 Memory + Diff）
2. **知识图谱跨条款矛盾**（conflict Agent）
3. **印章 / 签名合规审查**（OCR + 印章检测）—— 三者之中 OCR 是**唯一能靠「换一个开源项目」快速拉满**的

#### 3.2.1 一处被低估的巧妙设计：分数口径

`[实读]` `service.py` 注释明确指出：

> `final` 用 **clamp** 而非 `(x+1)/2` 映射：后者会把「无关文本」（余弦≈0）抬到 0.5，
> **直接击穿 0.35 阈值，使「缺失标准对照」信号失效**。

这条注释说明作者理解「**缺失检测**」在本业务里是**主动功能**（合同缺什么条款），而不是失败路径。
全仓最值得保留的设计思想之一。

#### 3.3.1 已实现但需要你知道能力边界的三处

1. **`HashEmbedder` 是默认，且它不是语义模型**。`[实读]` 它用 blake2b hashing trick 生成确定性伪向量，
   能表达「共享词汇越多越相似」，**不能表达同义/近义**。它的存在意义是「零依赖跑通链路」。
2. **`BM25Store` 是自研纯 Python**。`[实读]` 复用 `rag_core.adapters.embedding.tokenize`（拉丁词 + CJK 单字 + CJK 二元组），
   **不依赖 jieba**（jieba 实测未安装），pickle 单文件持久化，同 `chunk_id` 先删后写保证幂等。
   源码里有一句很诚实的注释：*内部实为「正排表全量扫描」而非倒排索引，docstring 已改以免误导维护者*。
   → **这是 O(N) 扫描**，语料上千条后需要关注性能。
3. **`NoopReranker` 是默认**。`[实读]` `factory.build_reranker()` 中 `rerank_mode="local"` 会**直接回退 noop 并打 warning**，
   因为项目红线禁止引入 torch / sentence-transformers。**精排能力目前等于零**。

## 6. 关键发现清单（按优先级排序）

> 每条发现都给出：**现象 → 证据 → 影响 → 建议动作**。P0 = 阻塞主线，P1 = 影响质量，P2 = 卫生问题。

### F1（P0）默认 RAG 是「非语义」的，达不到赛题召回指标

- **现象**：`CG_RAG_EMBED_MODE` 默认 `hash`，`CG_RAG_RERANK_MODE` 默认 `noop`。
- **证据**：`[实测]` 冒烟 3 条查询中 1 条 `EMPTY_RECALL`；`[实读]` `HashEmbedder` 是 blake2b hashing trick，
  `factory.build_reranker()` 对 `local` 模式直接回退 noop（因红线禁 torch）。
- **影响**：**当前形态无法满足「风险召回 ≥75%」**。RAG 链路是对的，但「语义」这一半为空。
- **动作**：必须补齐 ①真实 embedding 服务（bge-m3，1024 维）②HTTP reranker 服务（bge-reranker-v2-m3）。
  两者都要进 `docker-compose`（见推进文档 WS-A / D4）。

### F2（P0）BM25 独有命中被静默丢弃，混合检索价值被削弱

- **现象**：`[实读]` `service.py::_fuse()` 注释与代码明确写着：
  `"chunk_id 无法取回完整 ContractChunk（SparseHit 只有 text），只能丢弃"`
  并追加 warning `"N 条仅 BM25 命中的候选无法取回完整切片，已丢弃"`。
- **根因**：`rag_contracts/ports.py::SparseHit` **只有 `chunk_id` / `score` / `text` 三个字段，没有 `payload`**。
- **影响**：**这恰好打掉了 BM25 在本业务里最大的价值**——「第五百八十五条」这类**精确编号/专名检索**，
  而这类查询稠密向量恰恰最容易漏。混合检索退化成「稠密为主 + 稀疏仅用于重排已有候选」。
- **动作**：给 `SparseHit` 增加 `payload: dict[str, Any]`，并在 `_fuse()` 用
  `ContractChunk.from_payload()` 还原稀疏路独占候选（`ContractChunk.to_payload/from_payload` **已存在**，成本极低）。
  ⚠️ 注意：`SparseHit` 不在 4 份导出的 JSON Schema 之列，改它不触发「生成物红线」。

### F3（P0）`celery` 未安装 → `async-worker` 整体不可导入

- **证据**：`[实测]` `.venv` 无 celery；`[实读]` `worker/main.py` 顶层 `from celery import Celery`。
- **影响**：**整条异步链路（解析 / 审核 / 报告）无法启动**，这是所有端到端联调的前置。
- **动作**：`uv add --package async-worker celery`，并补 `redis`（已装）。

### F4（P0）`paddlepaddle` 未安装 → OCR 一行都跑不了

- **证据**：`[实测]` 只有 `paddleocr 2.10.0`（Python 包装层）与其周边（opencv / pyclipper / shapely / scikit-image），
  **无 `paddlepaddle`（推理引擎）**；`[实读]` `doc-processor/pyproject.toml` 也只声明 `paddleocr>=2.7`
  —— **依赖声明本身就不完整**。
- **影响**：OCR 是三大创新点之一，目前 0 能力。且 `paddleocr` 仅 import 不会报错，**会到调用时才炸**，容易误判。
- **动作**：见推进文档 WS-C（含「是否换用 PaddleOCR 3.x / RapidOCR」的选型对比）。

### F5（P0）`ai_engine` 缺依赖声明，`uv sync` 后必然 import 失败

- **证据**：`[实读]` `packages/ai-engine/pyproject.toml` 的 `dependencies` 只有
  `pydantic` / `langgraph` / `openai`，`[tool.uv.sources]` **为空**；
  但 `ai_engine` 将来必然要 import `rag_core` 与 `rag_contracts`。
- **影响**：CI / 容器 / 新同事拉代码后，`ai_engine` 一 import 就 `ModuleNotFoundError`。
- **动作**：补 `rag-contracts` / `rag-core` / `cg-observability` 声明与 `[tool.uv.sources]` workspace 引用
  （可直接照抄 `rag-core/pyproject.toml` 的写法）。

### F6（P1）`ai_engine/rag/*` 与 `rag_core` 是两套并行实现（架构分裂风险）

- **证据**：`[实读]` `rag_core` 是真内核（646 行 service + 7 个 adapter + 140 例测试）；
  `ai_engine/rag/{retriever,reranker}.py` 是空壳，docstring 还写「接入 Qdrant + BM25」——
  即**它描述的实现已经存在于 `rag_core` 了**。
- **影响**：后续 T04 极易出现「在 ai_engine 里再写一遍检索」的重复劳动与行为漂移。
- **动作**：**明确二选一并写进代码注释**：`ai_engine/rag/*` 降级为**薄桥接**（re-export `rag_core` 的 `RAGService`
  或提供 `build_agent_retriever()`），**禁止**在其中再实现检索逻辑。

### F7（P1）`ScopedClauseMemory` 有两份定义，必然漂移

- **证据**：`[实读]` `agents/rewriter.py` 与 `memory/scoped_memory.py` 各定义一份同名模型，
  且前者 `recentDialog: list[dict]`（弱类型）、后者 `list[DialogTurn]`（强类型）。
- **影响**：Agent 状态里到底用哪份会让序列化/校验行为不一致。
- **动作**：保留 `memory/` 一份为准，`agents/rewriter.py` 改为 import。

### F8（P1）8 个配置项「声明了但没人消费」

- **证据**：`[实读]` `RagSettings` 声明了 32 个字段，但 `factory.build_service_from_settings()` 只消费
  `dense_top / sparse_top / rrf_k / max_context_tokens`（外加 `bm25_*` / `embed_*` / `vector_store` / `rerank_enabled` / `rerank_mode`）。
  **未被任何代码消费**的包括：`strategy`、`score_threshold`、`rerank_threshold`、`rerank_top_n`、
  `timeout_ms`、`max_retries`、`max_query_chars`、`cache_ttl_s`。
- **影响**：⚠️ **这不是小事**——`CG_RAG_STRATEGY=HYBRID_RRF` 改了不会有任何效果（请求侧默认才是实际值）；
  更关键的是，**T04 设计的「Agent 三道防线」（超长拦截 / 超时重试 / 阈值降级）
  所依赖的 `max_query_chars` / `timeout_ms` / `max_retries` 目前没有任何引擎实现**。
- **动作**：推进文档 WS-B 的 T-B4 把这些配置真正接进服务与工具层（否则三道防线是纸面的）。

### F9（P1）前端缺 PDF 渲染底座，赛题「原文位置」无法交付

- **证据**：`[实读]` `web-ui/package.json` 无 `pdfjs-dist`（也无 `pdf-lib` / `react-pdf`）。
- **影响**：`BBox` 坐标虽已在契约层贯穿（`ContractChunk.bbox` → `RetrievedDoc.bbox` → 前端），
  但**没有渲染层承接**，「报告含原文位置 + 点击高亮」这一硬性交付无法完成。
- **动作**：加 `pdfjs-dist` + 一个 `usePdfOverlay` 组合式函数（推进文档 §3 WS-D 附带）。

### F10（P1）无 embedding / reranker 服务落地，`embed_mode=http` 无对端

- **证据**：`[实读]` `docker-compose.yml` 只有 postgres / redis / qdrant / minio / api / worker / web / nginx。
- **影响**：即使把 `CG_RAG_EMBED_MODE` 改成 `http`，也没有服务可连（默认 `http://localhost:8080` 会超时→降级）。
- **动作**：新增 TEI 或 Xinference / vLLM 容器提供 bge-m3 与 bge-reranker-v2-m3（推进文档 D4）。

### F11（P1）Milvus 决策与既有设计文档正面冲突（需你拍板）

- **证据**：`[实读]` `文件集合/report/RAG_MODULE_DESIGN.md` §1.3 标题即为
  「选型冲突对齐：Qdrant vs Chroma / PGVector / Milvus」，结论明确：
  **「Phase 3 不切 Milvus」**，理由是「换 Milvus = 重写索引建表 / payload schema / 过滤 DSL / 运维体系，
  代价 ≥ 2 人周且无业务收益」；§1.3.3 另给出「若坚持迁移」的 6 步清单（≈5 人日）。
- **影响**：本次需求要求「以 Milvus 为向量数据库核心」，**与已落盘的设计决策相反**。
  好消息是：因为 `VectorStorePort` 抽象存在，**实际代码代价远小于 2 人周**（新增 1 个适配器 + 改 DI），
  真正的代价在**运维复杂度**（Milvus 需要 etcd + 对象存储，且 Milvus Lite 在 Windows 上不可用）。
- **动作**：**不要把这条当成「推翻设计」，而是当成「一次有记录的技术决策变更」**。
  推进文档 §1 D1 给出完整对比、推荐路径与回退方案。

### F12（P2）`.venv` 不可直接启动 + 无 `pytest.ini` / 根 `conftest.py`

- **证据**：`[实测]` `.venv\Scripts\python.exe` 启动失败；

## 8. 总体评价与结论

### 8.1 这个项目的真实水平

**架构与契约设计：优秀（超过大多数同类赛题项目）。**
Ports & Adapters 用得克制且彻底；`chunk_id` uuid5 确定性、`text_hash` 增量、clamp vs 线性映射的阈值分析、
OpenAI strict 模式的 `$ref` 内联处理、降级即信号而非错误 —— 这些都是**踩过坑才会有的设计**。

**工程执行：两极分化。**
`rag-core` 一侧有 140 个测试全绿、有埋点、有降级、有冒烟脚本；
`ai-engine` / `doc-processor` / `async-worker` 一侧则是干净的空壳，连依赖都没装齐（celery / paddlepaddle）。

**最大风险不是技术难度，而是「文档与代码不同步」**（§7.4 已列 7 条）。
多份设计文档描述了一个**已被放弃的目录结构**（`rag-etl`），且多份工作日志的结论已过期。
**建议把本文档作为接手该项目时的「地面真值」索引**。

| 你的目标 | 与现有基线的匹配度 | 关键前提 | 预估量级 |
