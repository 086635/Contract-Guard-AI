## 6. 对您推进计划的校验与修正

您的计划：**后端 infra+API → 预留核心接口（OCR / LangGraph Agent / RAG）→ 前端布局样式 → 核心引擎三大功能开发**。

### 6.1 计划有效性判定

| 您的步骤                  | 判定             | 说明                                                                                                                               |
| --------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 后端 infra + API        | ✅ 方向对，需补 2 项   | 补：① `pnpm install` + 验证 `gen:zod`；② 路由绑定 `response_model`（从 `generated.schemas` import）并接 stub service，使 API 可返回真实结构（即便数据为 mock） |
| 预留核心接口（OCR/Agent/RAG） | ✅ 强烈推荐（接口先行）   | 用 **Protocol / 抽象基类** 固化接口，返回 mock，先让上下游打通；这正是降低联调风险的正确做法                                                                        |
| 前端布局样式                | ✅ 可行，但**前置依赖** | 必须先完成前端依赖安装 + 生成物校验，否则 `client.ts` 无法 `import` 类型、`vite` 起不来                                                                     |
| 核心引擎三功能               | ✅ 合理收尾         | 建议顺序 **OCR → RAG → Agent**（OCR 是上游数据源，RAG 是审核依据，Agent 负责编排）                                                                      |

### 6.2 关键修正建议

1. **前置依赖（阻塞项）**：`node_modules` 为 0。在"驱动前端"前必须 `pnpm install` 并跑 `pnpm --filter @contract-guard/schema gen` 确认 `zod.ts` 完整——否则前端寸步难行。
2. **"API 调试"的重新定义**：当前路由 501。建议先做 **Walking Skeleton**：路由绑定 `response_model` + 调用 stub service（返回生成 DTO 的假数据）→ 前端能拉到结构化响应 → 真正完成"API 驱动前端"。这比纯 501 联调更有价值。
3. **LangGraph 决策已落地（呼应 D2）**：您明确"基于 LangGraph 开发智能体引擎"，但 `ai-engine` 当前是普通函数。需在 Phase 2 用 `langgraph` 重构为 `StateGraph`（节点：classify → extract → audit → conflict → report），并将 `auditor/rewriter/conflict` 包装为节点。
4. **评分关键路径要并行**：工程关键路径是 OCR→RAG→Agent→前端；但**赛题得分关键路径是"模型+评测"**。建议从 Phase 1 起就并行启动：① 选定底座模型（Qwen/GLM 开源 or API）；② 准备标注样本集（CUAD/LeCaRD + 脱敏合同）；③ 搭评测脚本。这决定能否拿到"指标类"分数，且周期长，不能等到最后。

### 6.3 您提到的"文件集合内部开发文档要求"

赛题「提交材料」含：项目概要、PPT、详细方案、演示视频、使用说明、训练/微调记录、分工记录。这些**非代码交付物**应作为**独立并行工作流**从现在起建跟踪表（建议在 `文件集合/` 建 `deliverables/` 跟踪清单），避免临提交前突击。详细方案/使用说明可与当前架构报告同源复用。

## 7. 分阶段推进路线建议

### 阶段 A — 收尾 Phase 0（约 3–5 天）

- [ ] `pnpm install`（前端依赖）+ 校验 `gen:zod` 产出完整

- [ ] `docker compose up` 起基础设施（postgres/redis/qdrant/minio），验证连通

### 阶段 B — 后端业务骨架（Phase 1，约 2 周）

- [ ] `app/db`：SQLAlchemy Model + Alembic 初版迁移（Contract / Element / Risk / Conflict / Seal / Feedback / Version）
- [ ] `app/services`：合同服务、审核编排服务、报告服务；对接 Worker 任务发布
- [ ] 路由 501 → 真实逻辑（先打通 上传→解析触发→状态轮询 主链路）
- [ ] `async-worker`：`parse_doc` 先接 **mock doc\_processor**，保证链路可跑

### 阶段 C — 接口预留（与 B 并行，接口先行）

- [ ] `doc_processor` 定义 `DocumentParser` Protocol（`analyze/ocr/extract/align`），提供 mock 实现
- [ ] `ai_engine` 定义 `RiskAuditor` / `ClauseRewriter` / `ConflictAnalyzer` / `Retriever` / `Reranker` 抽象接口，提供 mock
- [ ] 这些接口即您说的"预留核心接口"，下游前端/API 可先against mock 开发

### 阶段 D — 核心引擎三功能（Phase 2，约 3–4 周，顺序 OCR→RAG→Agent）

1. **OCR/文档解析**：接入 PaddleOCR + PP-StructureV2 + pdfplumber，落实 `layout/ocr/parser/aligner` 真实逻辑；产出条款 AST + BBox。
2. **法务 RAG**：搭建 Qdrant + 嵌入；入库企业标准条款库 + 法条/裁判文书；实现 `retriever`(Dense+Sparse) + `reranker`(Cross-Encoder)。
3. **LangGraph Agent**：重构 `ai-engine` 为 StateGraph；classify→extract→audit→conflict→rewrite 节点化；接 LLM（PromptRoleConfig 可配置）+ RAG 上下文 + 分层 Memory。

### 阶段 E — 前端实现（Phase 3）

- 基于真实生成类型接 `client.ts`；填充 5 大页面与 3 组件；PDF.js BBox 高亮；AgentChat 多轮改写；反馈标注闭环。

### 阶段 F — 评分与交付（贯穿 + 收尾）

- 模型选型 + 标注集 + 评测脚本（分类/抽取/风险三类指标），目标达赛题阈值
- 提交材料并行产出（PPT/视频/使用说明/训练记录/分工）
