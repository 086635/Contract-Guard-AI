## ② 范围

### ✅ 做

- 校验合同存在。
- 校验 `CommitBody.items` 非空、item id 非空。
- 校验 `version` 与当前版本的兼容规则。
- 返回 OpenAPI `BatchResult`，保留局部失败语义。
- 以同一事务写入采纳结果并递增合同版本。

### ❌ 不做

- 不重写条款正文，不调用 Agent。
- 不把成功/失败项混成单一布尔。
- 不在没有版本表的情况下伪造“版本链”。

## ⑤ 接口规格

```python
class CommitService:
    async def commit(self, contract_id: UUID, body: CommitBody, request_id: str) -> BatchResult: ...
```

分区规则：

```text
accept=True  → successIds
accept=False → failedItems[reason="用户未采纳该修改项。"]
```

## ⑥ 实现规范

1. 响应只能由生成 DTO 构造，禁止手拼包络。
2. `version` 为空时按“不参与乐观锁”处理；提供时必须与当前版本比较。
3. 合同不存在返回 404，版本冲突返回 409/`ERR_DATA_CONFLICT`。
4. 如果落地版本表，写入与合同版本更新必须在同一事务。
5. 失败项 reason 必须是稳定、可展示的中文文本。

## ⑦ 验收标准

| # | 断言 |
|---|---|
| 1 | 不存在合同返回 404 |
| 2 | accept/reject 正确分入 successIds/failedItems |
| 3 | 相同请求重复提交不产生第二份状态 |
| 4 | version 冲突返回 409 |
| 5 | 若版本持久化未获批，测试明确 skip/标红“真实化不可完成” |

### 实测后回填

| 项 | 实测值 |
|---|---|
| 批次分区 | ✅ accept/reject 分别返回 `successIds` / `failedItems`（2026-09-27） |
| 版本持久化 | ✅ 合同版本从 1 递增到 2，提交明细落库（2026-09-27） |
| 幂等 | ✅ 同一 `X-Request-ID` 重放返回相同结果，版本与明细均不重复（2026-09-27） |
| 冲突与边界 | ✅ 旧版本 409、未知合同 404、空 items 422（2026-09-27） |
| 定向测试 | ✅ 真实 PostgreSQL **2 passed in 1.19s**；无 DSN 时 **1 passed / 1 skipped**（2026-09-27） |

## ⑧ 测试要求

- 覆盖 404、空 items、全 accept、混合 accept/reject、版本冲突。
- 幂等测试使用同一 `X-Request-ID`。
- 版本链测试在 schema 未落地前必须 skip 或明确失败，不得伪造 PASS。
