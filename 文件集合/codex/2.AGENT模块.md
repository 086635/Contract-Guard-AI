## 2.1 模块目标

把 `packages/ai-engine` 从「**5 个 `NotImplementedError` 空壳 + 零测试**」推进到
「**`audit_graph` 能对一份真实合同跑完 6 阶段，每条风险都带 CoT 推理链与 RAG 溯源**」，并让 `rewrite_graph` 支撑多轮条款改写。

### 2.1.1 对应赛题硬指标

| 赛题指标 | 阈值 | 本模块的支撑点 |
|---|---|---|
| 合同类型分类准确率 | ≥ 85% | `classify` 节点 |
| 关键要素抽取 F1 | ≥ 80% | `extract` 节点（**必须回填 `bbox` + `confidence`**，否则前端无法高亮） |
| 风险条款识别 召回 / 精准 | ≥ 75% / 75% | `risk_node`（逐条款 + **每条都调 RAG Tool**） |
| 报告含原文位置 | 必须 | `EnhancedRiskItem.bbox` ← OCR 模块供给 |
| 报告含法律依据 | 必须 | `EnhancedRiskItem.citations` ← RAG Tool |
| **多 Agent 协作** | 必须 | `audit_graph` 6 阶段 + `rewrite_graph`（**赛题显式要求，不是加分项**） |
| 每步可解释（CoT） | 必须 | `ReasoningStep[]`（**模型已有，禁止另造**） |

### 2.1.2 本模块的四个关键词

```text
定形态   —— 自绘 StateGraph + 6 阶段固定流水线（不用 create_react_agent）
收版本   —— langgraph 声明 0.2 → 钉死到实测的 1.2.x（跨大版本 API 不兼容）
单一入口 —— ai_engine/llm/ 是唯一模型构造点，禁止在节点里 new 模型
落防线   —— RAG Tool 的「三道防线」目前只存在于文档里，必须真正实现
```

### 2.1.3 编排形态（**依据 D2 的推荐，待你确认**）

🔴 **不用 `create_react_agent`，用自绘 `StateGraph`。**

| 候选 | 采用 | 理由 |
|---|---|---|
| `langgraph.prebuilt.create_react_agent` | ❌ | 自由 ReAct 循环，**无法保证阶段顺序与产出完整性**；赛题要求固定流水线 + 每步 CoT + 每步溯源 + 可降级 |
| **自绘 `StateGraph`（6 节点固定拓扑）** | ✅ | 确定性阶段 + 可控降级 + 可挂 checkpointer；**赛题本身要求"多 Agent 协作"，自绘图更能体现设计能力** |

**audit_graph 拓扑（固定 6 阶段）**：

```text
START → classify → extract → risk_node → conflict_node → standard_compare → report_draft → END
```

| 节点 | 职责 | 对应指标 |
|---|---|---|
| `classify` | 合同类型分类，写 `state.contract_type` | 分类准确率 ≥85% |
| `extract` | 要素抽取（含 `bbox` / `confidence`） | 要素 F1 ≥80% |
| `risk_node` | **逐条款**风险识别（内部调 RAG Tool） | 风险召回/精准 ≥75% |
| `conflict_node` | 跨条款矛盾（**先粗筛、后精判**） | — |
| `standard_compare` | 标准条款比对 + **缺失检测** | 缺失条款提醒 |
| `report_draft` | 汇总 + 健康分（**纯聚合，不调 LLM**） | 可复现 |

> 🔴 **`risk_node` 与 `conflict_node` 的两条性能红线**（见 `2-4` 详述）：
> ① **不要为每个条款建一个 Graph 节点** —— 节点数会运行时爆炸、checkpoint 巨大；Graph 只保留 6 个固定阶段。
> ② **`conflict_node` 禁止 O(n²) 全对比较** —— 100 条条款 = 4950 次 LLM 调用，不可接受。
> 必须「**先规则粗筛（付款 / 责任 / 期限关键词）→ 后 LLM 精判**」，把候选对压到 20~50 对以内。

## 2.4 端到端数据流

### 2.4.1 审核流（audit_graph）

```text
worker.run_audit_task(contract_id)
  ├─ 载入 GlobalContractState（AST 拓扑）                  ← 2-8 Memory 外部化
  ├─ 构造 AuditState（clauses 来自 doc_processor）          ← 3.OCR模块 供给
  └─ graph.invoke(state, config={"configurable": {"thread_id": contract_id}})
        ├─ classify         → contract_type
        ├─ extract          → elements[]（含 bbox/confidence）
        ├─ risk_node        → risks[]（**逐条款**，每条调 RAG Tool）
        ├─ conflict_node    → conflicts[]（规则粗筛 → LLM 精判）
        ├─ standard_compare → missing_clauses[]（**用 EMPTY_RECALL 作缺失信号**）
        └─ report_draft     → report_draft + health_score（纯聚合，不调 LLM）
```

> ⚠️ **`standard_compare` 是本项目"缺失条款提醒"的实现机制**：
> RAG 返回 `EMPTY_RECALL` 或低分命中 → 即判为「**缺失标准对照**」。
> 这正是 `0.§0.5.1` 把 `EMPTY_RECALL` 称为**握手信号而非错误**的原因。

### 2.4.2 改写流（rewrite_graph）

```text
API.post("/agent/rewrite", AgentRewriteRequest)
  → worker / 同步调用 rewrite_clause(req)
     ├─ 载入分层 Memory：
     │    全局层 GlobalContractState（合同元信息 + AST 拓扑）
     │    局部层 ScopedClauseMemory（**仅当前条款近 3-5 轮**）
     ├─ RAG Tool 取对照条款（可选）
     └─ rewrite_graph.invoke(config={"configurable": {"thread_id": f"{contract_id}:{clause_id}"}})
           → RewriteResponse（before / after / diff / reasoningSteps / citations）
```

> ✅ **`thread_id` 用 `f"{contract_id}:{clause_id}"` 组合** —— 这正好对应
> `ScopedClauseMemory` 的「**条款级作用域**」设计，天然实现分层 Memory 的「局部上下文」那一层。
> **别只传 `contract_id`**，否则同一合同下多个条款的改写会互相污染。

| **D2-d** | LLM 供应商与模型名（填 `CG_LLM_*`）；**注意 JSON 结构化输出的稳定性** | T-B1 / T-B3 | ✅ **已拍板（2026-09-21）**：**DeepSeek `deepseek-flash`**（`https://api.deepseek.com/v1`，key 只进 `.env`） |

> 🔴 **D2-d 是本模块最大的不确定性**：风险识别靠 LLM 结构化输出，
> **模型对 `with_structured_output` 的稳定性直接决定「召回 ≥75%」能否达标**。
>
> 🔬 **实测结论（2026-09-21 本机真调 `deepseek-flash`，两条硬约束必须写进 `2-2`）**：
> 1. **`response_format={"type":"json_schema"}` 不可用**（HTTP 400 `This response_format type is unavailable now`）
>    → `.with_structured_output(...)` **必须显式走 `method="function_calling"`**；`{"type":"json_object"}` 可用且 JSON 可解析。
> 2. **`deepseek-flash` 是 reasoning 模型**：`reasoning_tokens` 先占 `max_tokens`，`max_tokens=16` 时 `content` 直接是空串
>    → `CG_LLM_MAX_TOKENS` 必须有下限（建议 ≥ 2048），并把「空 content + reasoning 拉满」判为截断。
> 选型时应优先验证"复杂 Pydantic 嵌套模型能否稳定产出"，而不是只看模型榜单。
