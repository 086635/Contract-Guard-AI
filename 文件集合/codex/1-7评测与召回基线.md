## ⑤ 指标定义（**口径必须写死，否则数字不可比**）

### 5.1 Recall@K

```text
对每条 query：
    hit@K = 1 if (gold_chunk_ids ∩ top_K_retrieved_ids) != ∅ else 0

Recall@K = mean(hit@K)  over all queries
```

> **采用「命中即算」口径（hit-rate）**，而非「召回 gold 的比例」。
> 理由：本场景每个 query 通常只对应 1~3 条标准条款，
> 「只要 top-K 里出现任意一条正确的，该 case 就算过」更贴近业务判断。
> ⚠️ **口径一旦选定不得中途更改**，否则历史数字不可比。

### 5.2 MRR（Mean Reciprocal Rank）

```text
对每条 query：
    rr = 1 / rank_of_first_gold   （top-K 内没有 gold 则 rr = 0）

MRR = mean(rr) over all queries
```

> MRR 反映「正确结果排得够不够靠前」——这对本场景尤其重要，
> 因为 `rerank_top_n` 默认只取 5 条注入 Prompt，**排到第 6 位等于没召回**。

### 5.3 建议同时记录

| 指标 | 用途 |
|---|---|
| `Recall@1 / @3 / @5 / @10` | 观察排序质量曲线 |
| `avg_top_score` | 观察分数分布，辅助阈值标定 |
| `empty_recall_rate` | **直接对应"缺失标准对照"信号的质量** |
| `avg_latency_ms` | 观察各阶段耗时（`stage_latency_ms` 已内建） |

## ⑥ gold set 格式规格

### 6.1 JSONL 结构（每行一条）

```json
{"query_id": "q001", "query": "买方逾期付款的违约金怎么约定，上限是多少", "gold_chunk_ids": ["a1b2c3d4-....-...."], "contract_type": "PURCHASE", "source_types": ["STANDARD_CLAUSE", "LAW_ARTICLE"], "note": "对应标准条款 6.2"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `query_id` | ✅ | 唯一标识，用于逐条对比与回归 diff |
| `query` | ✅ | 检索文本（模拟真实待审条款或用户提问） |
| `gold_chunk_ids` | ✅ | 期望命中的 `chunk_id` 列表（**至少 1 条**） |
| `contract_type` | ⭕ | 传给 `RetrievalFilters`，用于同类型优先 |
| `source_types` | ⭕ | 限定检索源 |
| `note` | ⭕ | 人工备注，便于复核 |

### 6.2 标注集规模建议

| 阶段 | 条数 | 说明 |
|---|---|---|
| 冒烟 | 10 | 够跑通脚本，数字仅供 sanity check |
| **基线** | **≥ 50** | **正式基线的下限**（赛题评审可引用） |
| 充分 | 100~200 | 分难度分层（简单/需推理/易混淆） |

### 6.3 🔑 无人工标注时的自构造方法（**推荐先用这个**）

> 现实问题：人工标注 50 条耗时且需要法务参与。
> **下面这个方法可以在 10 分钟内产出可用的弱标注集**，先把评测闭环跑起来。

**方法：以标准条款原文自身作为 query。**

```text
对每条标准条款 chunk：
    query = 该 chunk 的标题 + 前 N 个字符（或整条 text）
    gold_chunk_ids = [该 chunk 自己的 chunk_id]

原理：若检索系统正常，用条款原文去检索，应该能找回它自己。
      这测的是「检索链路是否接通 + 向量是否可用」，属于【下限测试】。
```

| 优点 | 局限 |
|---|---|
| 零人工成本，立即可用 | **会高估**真实表现（原文 query 太"容易"） |
| 可作**回归门禁**（防止改坏） | 不能替代人工标注做最终验收 |
| 能立刻暴露"向量没生效/库没连上"这类致命问题 | — |

> ✅ **建议做法**：
> ① 先用弱标注集建立**回归门禁**（防止改坏）；
> ② 再补 50 条**人工标注**作为**验收基线**。
> 两者**分别记录、不得混淆**。

**生成方式**：可直接复用 `scripts/phase1_smoke.py` 的语料加载逻辑
（`load_corpus` + `SimpleChunker`），把每个 chunk 转成一行 gold，无需新写解析代码。

## ⑦ 脚本规格

### 7.1 命令行接口

```text
python scripts/eval_recall.py \
    [--gold scripts/data/gold.jsonl] \
    [--corpus scripts/data/phase1_sample.jsonl] \
    [--top-k 5] \
    [--cutoffs 1,3,5,10] \
    [--strategy DENSE_ONLY|HYBRID_RRF] \
    [--threshold 0.35] \
    [--out reports/eval_YYYYMMDD_HHMMSS.json] \
    [--baseline reports/eval_baseline.json]
```

### 7.2 执行流程

```text
1. 加载语料 → SimpleChunker.chunk() → ContractChunk[]
2. build_service_from_settings() → RAGService
3. ensure_collection(dim) + embed_batch + upsert（向量库为空时；已存在则跳过）
4. 逐条 query 调 retrieve()，收集 retrieved_docs 的 chunk_id 序列
5. 计算 Recall@1/3/5/10、MRR、empty_recall_rate、avg_top_score、avg_latency_ms
6. 输出：控制台表格 + JSON 文件（便于回归 diff）
7. 若提供 --baseline：与基线逐条对比，退化超阈值则非零退出码
```

### 7.3 输出 JSON 结构

```json
{
  "meta": {"created_at": "...", "config": {"vector_store": "qdrant", "embed_mode": "http", "rerank_mode": "http", "strategy": "HYBRID_RRF", "collection": "contract_clauses"}, "gold_file": "...", "gold_count": 52},
  "metrics": {"recall@1": 0.0, "recall@3": 0.0, "recall@5": 0.0, "recall@10": 0.0, "mrr": 0.0, "empty_recall_rate": 0.0, "avg_top_score": 0.0, "avg_latency_ms": 0},
  "per_query": [{"query_id": "q001", "rank_of_first_gold": 2, "rr": 0.5, "hits": 5, "degraded": false, "top_score": 0.0, "took_ms": 0}],
  "regression": {"baseline_file": "...", "recall@5_delta": 0.0, "regressed": false}
}
```

> ⚠️ **必须把生效配置写进 `meta.config`**。否则不同配置跑出的数字混在一起无法比较 ——
> 这是评测脚本最常见的失效原因。

### 7.4 回归门禁

```text
if baseline is provided:
    delta = current.recall@5 - baseline.recall@5
    if delta < -0.05:        # 允许 5 个百分点的波动
        打印逐条退化明细（哪些 query_id 从命中变未命中）
        exit 1
```

> 💡 **逐条退化明细比总指标更有用**：它直接告诉你"哪一类问题变差了"。

### 8.3 达标的判断依据

| 赛题指标 | RAG 侧的可测量代理指标 | 目标 |
|---|---|---|
| 风险条款识别召回率 ≥ 75% | **Recall@5**（检索层，人工标注集） | **≥ 0.80**（留出余量给上层） |
| 风险条款识别精准度 ≥ 75% | 结合 `score_threshold` 的 precision | 待 Agent 层联合评估 |
| 缺失条款提醒 | `empty_recall_rate` 的**合理性** | 该空召回的确实空（人工抽查） |

> ⚠️ **RAG 侧的 Recall@5 目标设 0.80 而非 0.75**，因为上层 Agent 还会有损失，
> 检索层必须留出余量。检索层刚好 0.75，端到端几乎不可能达标。

## ⑩ 避坑清单

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 不记录生效配置 | 不同配置的数字混在一起，**不可比** | 必须写进 `meta.config` |
| 2 | 把弱标注集的数字当验收基线 | **高估**真实表现，误导决策 | 两类标注集**分开记录** |
| 3 | 中途更换 Recall 口径 | 历史数字失效 | 口径**先写死**（§⑤） |
| 4 | 用 `doc_id` 而非 `chunk_id` 作 gold | 粒度太粗，无法判断是否命中"那一条" | **用 `chunk_id`** |
| 5 | 担心重建索引后 gold 失效 | 白担心 | `chunk_id` 是 **uuid5 确定性生成**，重建后不变 |
| 6 | 把评测脚本塞进 `pytest` | 单测变慢，且可能因服务缺失而失败 | 独立脚本 + 手动/CI 定时 |
| 7 | 只在"全部命中"时才算通过 | 指标粒度太粗，无法定位问题 | 逐条记录 `query_id` 与 `rank_of_first_gold` |
| 8 | 把 RAG 的 Recall@5 目标直接设为 0.75 | 上层有损失，端到端**必然不达标** | 检索层目标 **0.80**，留余量 |
| 9 | 只在改后跑一次评测 | 无对比，不知道改动是否有效 | **改前也跑一次**，形成对照 |

### ⑪.2 两处**口径补强**（实测后才暴露）

1. **`rerank_top_n` 必须跟着 `--top-k` 放大**：`_rank()` 在精排生效时按 `rerank_top_n`（请求默认 5）截断，
   若照抄 `--top-k 10` 而不动它，**Recall@10 恒 ≤ 5**。脚本已固定 `top_k = rerank_top_n = max(cutoffs)`
   并记入 `meta`。
2. **基线可比性**：`meta.config_fingerprint` = 哈希(**配置 + 语料内容 + 标注集内容**) ——
   防止"拿 hash 的基线比 http 的结果"或"拿弱标注的基线比人工标注的结果"；不一致即**退出码 2**
   （`--force` 可越过）。

### ⑪.3 三条**编排器/工程**发现（已登记，未越界改）

1. 🔴 **`strategy` 目前不 gate 融合路径**：`RAGService.retrieve()` 无条件执行 dense + sparse + `_fuse()`
   （`service.py:193-197`），`strategy` 只进日志、以及"无稀疏库时强制降级 DENSE_ONLY"（`service.py:174-176`）。
   → **`DENSE_ONLY` 与 `HYBRID_RRF` 今天在排序上无差别**；因此 §8.2 的两行差异**只能归因于语义栈与精排**，
   **不能**归因于策略。建议由 C8/T-A7 的 owner 单独立项修正（本次未动 `service.py`）。
2. ⚠️ **精排成本随"融合候选数"而非 `rerank_top_n` 增长**：`_rank()` 把**全部候选**（`dense_top ∪ sparse_top`，
   实测每查询 20~34 条）发给 `/rerank`，实测每次 2.4~7 s，CPU 争用时可达 30~46 s ——
   121 条弱标注集的 http 跑一次耗时 **2389 s（约 40 分钟）**。
   → 演示/CI 要控时：调小 `CG_RAG_DENSE_TOP` / `CG_RAG_SPARSE_TOP`，或换 GPU / TEI。
3. ⚠️ **确定性口径**：默认输出**不含** `meta.created_at` 与任何耗时字段（`--with-timing` 才带），
   并静音 `rag_core` 埋点（`--json` 时），这样 stdout 是**纯 JSON 且两次运行逐字相同** ——
   §⑨ 的"确定性"要求据此可验收（否则时间戳/耗时必然破坏逐字比对）。
