## ⑥ 实现规范

服务定义以 `1-4 §⑤` 为准，要点：

- `etcd`：镜像 `quay.io/coreos/etcd:v3.5.16`，挂 `etcddata`，健康检查 `etcdctl endpoint health`。
- `milvus`：镜像 `milvusdb/milvus:v2.5.4`（**不用 latest**），`command: ["milvus", "run", "standalone"]`，端口 `19530`（gRPC 业务）/ `9091`（健康检查），复用 `minio`，挂 `milvusdata`。
- `milvus` 的 `depends_on`：`etcd: service_healthy`、`minio: service_started`。
- 健康检查：`curl -f http://localhost:9091/healthz`，`start_period: 60s`（冷启动 30~60 s）、`retries: 20`。

**启动竞态四条（必须写进文档语义，实现时遵守）**：

1. Milvus 冷启动慢 → 健康检查给足 `start_period` 与 `retries`。
2. `api` / `worker` 对 milvus 若用 `service_started` 会抢跑 → 本卡**不引入**该依赖，保持应用层容忍竞态。
3. 首次检索静默降级是预期行为 → 排查先看 `fallback_reason`，`STORE_UNAVAILABLE` 即 Milvus 未就绪。
4. 端口 `9091` 冲突会导致健康检查失败 → 起服务前检查占用。

## ⑩ 落地记录（2026-09-23 实测）

### 10.1 起服务：真机跑通，三条容器全部 healthy

```text
$ docker compose -f docker/docker-compose.yml up -d etcd minio milvus
contract-guard-etcd-1     quay.io/coreos/etcd:v3.5.16   Up (healthy)
contract-guard-milvus-1   milvusdb/milvus:v2.5.4        Up (healthy)   # 冷启动约 60 s
contract-guard-minio-1    quay.io/minio/minio:latest    Up
```

### 10.2 🔴 纠偏 1：必须显式固定 compose 项目名（本卡新发现的**高危坑**）

**现象**：本文件位于 `docker/` 下，compose 默认用**文件所在目录名**作项目名，即默认为 `docker`。
**实测**：本机另有一个同样放在 `docker/` 目录下的 compose 项目——Dify
（`D:\Dify\dify\docker\docker-compose.yaml`），其默认项目名**恰好也是 `docker`**，
`docker compose ls` 实测显示 `docker  running(11)`。

**后果**：两个栈共用命名空间 → 本项目 `up` 会把 Dify 的 11 个容器当成 orphan 提示清理；
`down` 更会**直接停掉 Dify 整栈**。

**处置**：在 `docker/docker-compose.yml` 顶部加 `name: contract-guard`（配注释说明原因）。
实测生效：`docker compose ls` 变为 `contract-guard running(3)`，与 `docker running(11)` 完全隔离，
容器名也带上 `contract-guard-` 前缀。**此条已写进仓库文件注释，勿删。**

### 10.3 纠偏 2：MinIO 镜像改用 Quay 仓库（本机网络限制，非设计变更）

**现象**：`minio/minio:latest` 拉取失败，报 `error from registry: denied`。
**实测**：本机 Docker 走 CN 加速器（`docker.m.daocloud.io` / `hub-mirror.c.163.com` / `mirror.baidubce.com`，
由 `docker info` 的 `RegistryConfig` 读出），该加速器对 Docker Hub 的 `minio/minio` 拒绝服务；
而 `quay.io/minio/minio:latest` **直连可拉**。

**处置**：改 `image: quay.io/minio/minio:latest`。**同一个官方镜像、同一条 `server /data` 命令、
同一组 `MINIO_*` 环境变量，行为不变**，故不违反 §⑨-4「保留既有服务」。
`milvusdb/milvus:v2.5.4` 与 `quay.io/coreos/etcd:v3.5.16` 均可正常拉取，无需改动。

### 10.4 🔴 验收副产物：发现 `MilvusVectorStore.count()` 在真服务上口径错误（**归属 T-A1，下游 T-A4 会被它卡住**）

本卡 §⑦-2 的连通性验证顺带用**本仓适配器**（而非裸 `MilvusClient`）做了一次真机联调，
发现 `count()` 的实现口径与真实 server 行为不符。对照实验（真 server v2.5.4，同一集合）：

| 时点 | `get_collection_stats()['row_count']`（**现实现**） | `query(filter="", output_fields=["count(*)"], consistency_level="Strong")` |
|---|---|---|
| 空集合 | 0 | 0 |
| `upsert` 3 条后**立刻** | **0** ❌ | **3** ✅ |
| `flush()` 后 | 3 | 3 |
| 同主键再 `upsert` 1 条后立刻 | 0 ❌ | 3 ✅（幂等，不增长） |
| `delete` 3 条后立刻 | **0** ❌ | **0** ✅ |
| `delete` 后 `flush()` | **3** ❌（含**已逻辑删除**的行） | 0 ✅ |

**结论**：`row_count` 是**物理行数**（含逻辑删除）且**未 flush 前为 0**，两处都与
`QdrantVectorStore.count()`（存活点数、即时一致）语义不符；`count(*)` 聚合查询 + `Strong` 一致性
在**不 flush** 的前提下即给出正确的存活实体数。

**为何在本卡登记**：`0-C3`（T-A4）的断言 2「同一 `chunk_id` `upsert` 两次 → `count()` 仍为 1」
与断言 6「`delete_by_doc()` 后 `count()` 减少」**都在真 server 上依赖 `count()`**，
而 `0-C3` §④ 明确「不改生产代码」→ 必须先修 `count()`，`0-C3` 才可能全绿。
**建议顺序：先落一笔 `fix(T-A1)`（改 `milvus_store.count()` + 回填 `1-2`/`1.C5` 偏差表），再进 `0-C3`。**
