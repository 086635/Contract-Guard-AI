### 0.1.4 三层文档体系：任务层与**组件层**（2026-09-21 增补）

**为什么要加第三层**：`N-M` 任务层的粒度是「**交付批次**」（0.5~3 人日，跨多个技术点），
用它直接驱动 goal 会出现「一个 goal 要同时搞定配置、装配、算法、测试」——**单次 goal 过大**。
组件层把每个任务切成**一个技术点 = 一个 goal**（0.2~0.5 人日）。

| 层 | 文件 | 回答什么问题 | 粒度 | 驱动方式 |
|---|---|---|---|---|
| **模块层** | `N.<模块名>.md` | 这个模块是什么、边界在哪、有哪些组件与任务 | 模块 | **Plan** 的输入（拆任务、排依赖） |
| **任务层** | `N-M<子任务名>.md` | 这一批交付什么、**跨组件**如何验收 | 0.5~3 人日 | 批次里程碑 |
| **组件层** | `N.C<k><组件名>.md` | 这一个技术点怎么做、**本组件内**如何自证 | 0.2~0.5 人日 | **一个 goal 一张卡** |

**命名**：`N.C<k><组件名>.md`，`k` 是模块内组件序号（**按依赖顺序编号，上游在前**）。

**三层之间不允许重复定义**（`0.§0.7` 的同一条规则向外延伸）：

- 组件卡**只写本组件**：接口、规则、断言、回填。**不复述**模块架构与任务范围。
- 组件卡的 `§⑦ 验收标准` = **组件内可自证**（单元级、离线可跑）；
  任务文档的 `§⑦` = **跨组件集成**（批级）。**两层断言范围不同，不构成重复**。
- 组件卡与任务文档的落点**必须一致**；不一致 → 按 `0.§0.11.2` 裁决，禁止各写一份。

**组件卡的章首块（强制，9 节之前）**：

```text
> 所属模块：<N 模块名>　组件 ID：**C-<k>**　归属任务：**T-xx**（`N-M`）
> 上游组件：C-xx（提供什么）｜下游消费方：C-xx / 模块 x
> 是否触碰契约层：❌ 否 / ⚠️ 是（只允许改什么）
> 落点：<精确文件路径>
```

**组件层的三条硬约束**：

1. 🔴 **一张卡一个 goal**：卡内工作量若超过 0.5 人日 → 说明还没拆够，继续拆（拆到能一轮做完为止）。
2. 🔴 **卡必须自带"适配性三问"**：① 只能往哪个方向 import？② 复用了哪些既有唯一处符号？
   ③ 明确不许新造什么？—— 这三问答不上来，说明该技术点与项目脱节。
3. 🔴 **卡不写"未来会加"**：只描述本次要落地的行为；后续增强写进模块总纲的组件索引备注。

### 0.1.5 组件覆盖率与"不制造空文档"原则

- 组件卡**只为"还没实现的组件"落盘**；已由任务层闭合的组件（如模块 3 全部组件）只在模块总纲
  的组件索引里登记「落点 + 证据（测试文件/用例名）」，**不再单独立文** —— 否则就是制造空文档。
- 每个模块总纲必须有 **`§X.5.1 组件索引`**：组件 / 目的 / 归属任务 / 上游 / 落点 / 组件断言数 / 人日 / 状态。
  它是 **Plan 的输入**：按上游优先排序，就是推荐的开工顺序。

> 依据：`packages/rag-core/rag_core/*.py` 与 `packages/rag-contracts/rag_contracts/*.py` 的既有写法。

### 0.2.1 文件结构

```python
"""模块一句话职责。

设计要点：
1. 要点一（**为什么**这样做，而非做了什么）。
2. 要点二。

对应：<设计文档> §<章节>。
"""

from __future__ import annotations

# 1) 标准库
# 2) 第三方
# 3) 本项目（rag_contracts / cg_observability / 本地相对导入）
```

| 规则 | 要求 |
|---|---|
| 模块 docstring | **中文**，首行一句话职责；随后用「设计要点」列 2~5 条 |
| `from __future__ import annotations` | **必须有**（全仓一致） |
| 导入分组 | 标准库 → 第三方 → 本项目，组间空一行（`ruff` isort 强制） |
| 行宽 | 88（`ruff` 配置；`E501` 已 ignore 但仍应对齐） |
| 类型标注 | **全量标注**，含返回值；可选参数用 `X \| None` |

### 0.2.2 函数 docstring（Google 风格 + 中文）

```python
def search(self, vector: Sequence[float], top_k: int) -> list[VectorHit]:
    """稠密检索。

    Args:
        vector: 查询向量。
        top_k: 返回条数上限。

    Returns:
        按得分降序的命中列表。

    Raises:
        StoreUnavailableError: 检索失败。
    """
```

| 规则 | 要求 |
|---|---|
| 段落 | 中文；`Args:` / `Returns:` / `Raises:` 三段**按需出现**（有才写） |
| 注释语言 | **中文** |
| 注释倾向 | 解释 **「为什么」**，而不是复述代码（范例：`service.py` 里解释为何用 clamp 而非 `(x+1)/2`） |
| `__all__` | 每个公开模块末尾必须有，按字母序 |

### 0.2.3 私有属性命名

- 实例私有字段用 `_snake_case`（如 `self._vector_store`）
- ⚠️ **重要**：`factory.build_service_from_settings(**overrides)` 通过反射访问 `f"_{key}"` 覆盖私有字段
  → **新增可覆盖字段必须命名为 `_<同名>`**，否则 overrides 静默失效

## 0.3 依赖方向红线

```
rag-contracts ──(被依赖)──> rag-core ──> ai-engine ──> async-worker
                                    ↑
                              api-gateway

doc-processor（解析层，被 ai-engine / async-worker 消费）
schema/openapi.yaml（SSOT → 生成 api-gateway DTO 与 web-ui TS/Zod）
```

| 红线 | 说明 |
|---|---|
| 🔴 **禁止反向依赖** | `rag-core` **不得** import `ai_engine` / `worker` / `apps/*` |
| 🔴 **禁止 SDK 泄漏** | `rag-core/rag_core/service.py` **只依赖 `rag_contracts.ports` 的 Protocol**，不得 import 任何具体 SDK（`qdrant_client` / `pymilvus` / `httpx`） |
| 🔴 **重依赖禁止入门** | `rag-core` **禁止** `torch` / `sentence-transformers` / `jieba` / `rank_bm25`（`pyproject.toml` 有明文注释）。需要精排 → **走 HTTP** |
| 🔴 **生成物不可手改** | `apps/api-gateway/app/generated/schemas.py`、`apps/web-ui/src/api/generated/{types.ts,zod.ts}` 由 CLI 生成 |

> **端口-适配器原则**：所有"会变的实现"（向量库 / 稀疏检索 / 向量化 / 重排）
> 一律实现 `rag_contracts.ports` 的 Protocol，并通过 `rag_core.factory` 装配。
> **换实现 = 加文件 + 加分支，绝不动 `service.py` 与 `rag_contracts`。**

## 0.5 错误、降级与可观测规范

### 0.5.1 错误体系（已存在，直接用，勿另造）

- 所有异常继承 `rag_contracts.errors.RagError`，携带 `code`（`CG-RAG-xxxx`）与 `retryable`
- 错误码常量见 `rag_contracts/errors.py`；**禁止在业务代码里写魔法字符串**
- **降级不是错误**：`EMPTY_RECALL`（`CG-RAG-2001`）是**握手信号**（表示"没有依据"），
  **不定义异常类**，只用于日志归因与 `RAGQueryResponse.fallback_reason`

### 0.5.2 降级红线

| 红线 | 说明 |
|---|---|
| 🔴 `RAGService.retrieve()` **永不抛异常** | 任何失败都必须转成 `degraded=True` 的响应 + `fallback_reason` + `warnings` |
| 🔴 适配器异常**必须包装** | 统一包装为 `StoreUnavailableError`（或对应错误类型），供上层降级判断 |
| 🔴 空召回必须给出提示语 | `context_block` 必须用 `rag_contracts.agent_tool.EMPTY_CONTEXT_HINT`（**单一真理源，禁止另写一份**） |

### 0.5.3 可观测（`cg_observability`，已存在）

```python
from cg_observability import TokenMeter, TraceContext, get_logger, log_event

_LOG = get_logger("rag_core.<模块名>")     # 命名空间与模块路径一致

log_event(_LOG, "<事件名>", trace_id=trace_id, candidates=20, top_score=0.87)
# 事件名风格：retrieve.start / retrieve.dense / retrieve.degrade / context.build ...
```

| 要求 | 说明 |
|---|---|
| 每个新阶段必须打点 | 至少含 `trace_id` 与 `latency_ms` |
| 耗时统一用 `meter.stage("<阶段名>")` | 阶段名沿用既有 6 个：`embed` / `dense` / `sparse` / `fusion` / `rerank` / `build` |
| 严禁吞异常不记日志 | `except` 分支必须有 `log_event(..., level="WARNING")` |

## 0.7 定义归属表（**「不出现重复定义」的核心机制**）

### 0.7.1 规则

> **任何一个概念/类型/常量，在仓库中只允许有唯一的定义处。**
> 其它文件**只能 import 引用**，禁止复制、禁止"为了自洽再写一份"、禁止在本模块内另立同名类。

### 0.7.2 定义归属清单（RAG 模块相关）

| 概念 / 类型 / 常量 | **唯一定义处** | 其它文件引用方式 |
|---|---|---|
| `SourceType` / `ChunkType` / `ContractType` / `RetrieveStrategy` / `FallbackReason` | `packages/rag-contracts/rag_contracts/enums.py` | `from rag_contracts.enums import ...` |
| `ContractChunk` / `BBox` / `EMBEDDING_DIM` / `SCHEMA_VERSION` | `packages/rag-contracts/rag_contracts/chunk.py` | `from rag_contracts.chunk import ...` |

| `RetrievalFilters` 的过滤语义 | `packages/rag-contracts/rag_contracts/query.py`（字段定义）＋ 各适配器（翻译实现） | 适配器各自 `_build_filter` / `_build_expr` |

## 0.11 文档权威层级（**消除「多份文档都自称唯一依据」的二义性**）

> ⚠️ **问题背景**：`文件集合/report/` 下曾有 **3 份文档各自宣称自己是「唯一依据」**：
>
> - `RAG_MODULE_DESIGN.md` —— 自称「契约与设计**唯一依据**」
> - `RAG搭建框架.md` —— 自称「**唯一**编码实施依据」
> - `RAG_IMPLEMENTATION_GUIDE.md` —— 自称「**可直接指导代码编写的实现圣经**」
>
> 而三者方向并不一致：前两者对齐 `rag_core`，第三份仍指向**已被废弃的 `packages/rag-etl/`**。
> **读者无法判断该信哪一份** —— 这是本项目最大的二义性来源。

### 0.11.1 权威层级（**冲突时以层级高者为准**）

| 层 | 文档 | 只在这些问题上**有权威** | 不得用于 |
|---|---|---|---|
| **L0 · 施工** | `文件集合/codex/*`（本文档体系） | **任务拆分、执行顺序、验收断言、落点** | 定义契约字段 |
| **L1 · 契约** | `RAG_MODULE_DESIGN.md` | **契约字段、接口签名、枚举取值** | 定实现细节、定命名 |
| **L2 · 实现** | `RAG搭建框架.md` | **标识符命名总表、算法实现细节** | 定义契约字段 |
| **L3 · 事实** | `项目代码深度阅读与分析报告.md` | **「仓库现在是什么样」（实测）** | 设计决策 |
| **L4 · 计划** | `codex项目推进.md` | **任务编号、决策登记（D1–D4）、开工门禁与模式编排（§12）** | 定义契约字段 |
| **L5 · 阅读** | `RAG白皮书.md` / `RAG对照解析.md` | 仅供**理解概念** | **任何实现依据** |
| **L6 · 历史** | `RAG_IMPLEMENTATION_GUIDE.md` / `AI核心开发文档.md` / `核心构建PRD.md` | 仅作**决策演进档案** | **任何实现依据** |

### 0.11.2 三条裁决规则

1. **L0~L2 之间不重叠**：L0 管「做什么 / 怎么算做完」，L1 管「字段长什么样」，L2 管「代码怎么写、叫什么名」。
   **三者不构成竞争** —— 所以「唯一依据」应各自限定在这三个**正交**的轴上。
2. **L5 / L6 不得被引用为实现依据**。若 L0~L2 出现空缺，**应补 L0~L2，而不是去 L6 找答案**。
3. **同一事实在多层出现且不一致时，以层级高者为准，并必须回头修正低层** ——
   修正方式一律为**追加「⚠️ 文档纠偏声明」**，**不删原文**（保留决策演进痕迹）。
