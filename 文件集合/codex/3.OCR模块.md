## 3.1 模块目标

把 `packages/doc-processor` 从「**6 个 `NotImplementedError` 骨架 + 零测试**」推进到
「**一份合同经 DOCX / 数字版 PDF / 扫描件任一路径，都能产出带精确 BBox 的要素、条款 AST 与印章检测结果**」。

> ⚠️ **本模块的名字容易误导**：它**不只是 OCR**。
> OCR 只处理"扫描件/图片"这一条支路；**数字版 PDF 与 DOCX 走的是直抽路径，比 OCR 更准更快**。
> 见 §3.4.1 分流决策 —— **这是本模块最容易做错的一步**。

### 3.1.1 对应赛题硬指标

| 赛题指标 | 阈值 | 本模块的支撑点 |
|---|---|---|
| 关键要素抽取 F1 | ≥ 80% | `NodeExtractor.extract_elements()`（甲乙方 / 日期 / 金额 / 期限 / 管辖地） |
| 报告含**原文位置** | 必须 | `BBoxAligner` 的 `(char_offset → BBox)` 索引表（**这是高亮闭环的关键**） |
| 条款结构化（AST） | 必须 | `NodeExtractor.extract_clauses()` → `ParsedClause` 拓扑 |
| 印章真伪 / 主体一致性 | 创新点 | `SealDetection`（**三段式自研，无现成方案**） |
| 多格式支持（DOCX/PDF/图片） | 必须 | `DocRouter` 四条支路 |

### 3.1.2 本模块的四个关键词

```text
先分流   —— 数字版 PDF 直抽，绝不对所有 PDF 都跑 OCR（很多团队在这里白白引入误差）
坐标归一 —— 三个来源的坐标统一到 PDF_POINTS（72dpi 左上原点）
补索引   —— (char_offset → BBox) 索引表：前端高亮的最后一块拼图
印章自研 —— 颜色分割 + 极坐标展开 + 模糊比对，全程无需深度学习模型
```

### 3.1.3 选型（**依据 D3 的推荐，待你确认**）

| 路线 | 选择 | 理由 |
|---|---|---|
| **主路线** | **PaddleOCR 3.x（PP-OCRv5 + PP-StructureV3）** | 中文准确率更优；PP-StructureV3 直接给版面区域，正好对上 `BlockType` 枚举 |
| **降级 / 兜底** | **RapidOCR**（ONNXRuntime 版） | 纯 onnx、无需 `paddlepaddle`、安装极轻。**它让"OCR 不再是必须装 paddlepaddle 才能跑的单点"** |
| **印章** | **必须自研**（三段式） | 通用 OCR 项目**都不提供印章文字识别**能力 |

> ⚠️ **`PaddleOCR` 2.x → 3.x API 不兼容**：`PaddleOCR()` 构造参数与 `ocr()` 返回结构都变了。
> 若选 3.x，适配器必须做**结构兼容层**，并把版本**钉死**在 `pyproject.toml`（勿用 `>=` 敞口）。
> 现状声明是 `paddleocr>=2.7`，**需同步修改**。

## 3.4 端到端数据流

### 3.4.1 分流决策（**本模块最容易做错的一步**）

```text
输入文件
  ├─ .docx                        → DOCX         → python-docx（结构化程度最高，无需 OCR）
  ├─ .pdf + 抽样页平均可抽字符 ≥ 50 → PDF_NATIVE   → pdfplumber（逐词坐标，精度最高）
  ├─ .pdf + 几乎无文本层            → PDF_SCANNED  → pypdfium2 渲染 → OCR
  └─ 图片                          → IMAGE        → 直接 OCR
```

🔴 **红线：绝不对所有 PDF 都跑 OCR。** 数字版 PDF 直抽**更准、更快、坐标天然精确**。
`RouteDecision.reason` 必须写进日志，便于排查"为什么这份走了 OCR"。

> 💡 **PDF → 图片请用 `pypdfium2`（已安装）**，**不要引入 `pdf2image`**：
> 后者依赖外部 poppler 二进制，**Windows 上部署极麻烦**；`pypdfium2` 是纯 pip 包、自带二进制、零外部依赖。

### 3.4.2 坐标体系（**改坐标相关代码前必须理解**）

**统一目标坐标系**：**PDF 用户空间（`PDF_POINTS`）** —— 72 dpi、**左上原点**。
契约字段：`NormalizedBBox.coordinate_system = "PDF_POINTS"`（默认值即此，勿改）。

| 来源 | 原生坐标系 | 换算到 PDF_POINTS |
|---|---|---|
| `pdfplumber` | 已是 72 dpi（PDF 用户空间） | **无需换算**（`src_dpi=72`） |
| `python-docx` | 无坐标，仅有段落顺序 | ⚠️ **需版面推断**（无真值，建议只在 DOCX 路径降级使用顺序定位） |
| OCR / 渲染图 | **像素**（取决于渲染 DPI） | `72 / render_dpi` 缩放 —— **渲染 DPI 必须从引擎一路传下来** |

🔴 **两个必须做对的地方**：

1. **渲染 DPI 不能丢**。引擎构造时记下 `self._dpi`，OCR 输出的像素坐标必须经
   `to_pdf_points(..., src_dpi=render_dpi)` 归一化。**丢了 DPI，所有框会整体错位。**
2. **`(char_offset → BBox)` 索引表是前端高亮的前提**。
   前端拿到的是「第 N 到第 M 个字符」，**必须靠这张表换算出 BBox 列表**才能画高亮框。
   ⚠️ 注意：`ContractChunk.bbox` 是**整条条款的框**，**不是命中句子的框** ——
   要句子级高亮，这一步不可省。

> 🔴 **不要自己写缩放**：一律复用 `BBoxAligner.to_pdf_points()`（已实现且有正确语义）。

### 3.4.3 印章检测（**创新点，无现成方案**）

三段式，**全程不需要深度学习模型**：

```text
① 区域检测  HSV 红色掩膜（红色跨 0/180 两端，需两段 inRange 取并集）
            → 形态学闭运算（印章常被签名/文字遮挡）
            → 轮廓筛选（面积 / 圆度）
② 文字识别  极坐标展开（把圆环拉直成水平文本条）→ 送通用 OCR
③ 主体比对  与合同甲乙方名称做模糊匹配（difflib.SequenceMatcher，零依赖）
            → 判定「印章与签约主体是否一致」
```

> 💡 **为什么极坐标展开是关键**：展开后印章的环形文字变成**一行水平文字**，
> 通用 OCR 的识别率会**大幅提升**（它本来就是为水平文本设计的）。
> 这是印章识别的标准技巧，且 `opencv`（已装）就能全部实现。

## 3.8 与其他模块的边界（**越界 = 返工**）

| 邻接模块 | 本模块**可以** | 本模块**不得** |
|---|---|---|
| **1 · RAG** | 产出 `ContractChunk` 所需的文本与 BBox；**复用** `simple_chunker._CLAUSE_HEAD_RE` 识别条款编号 | 🔴 **另写一套条款编号正则**（否则"解析层认为的第 3 条 ≠ 检索层认为的第 3 条"）；🔴 自己建检索索引 |
