## ⑤ 模型与形态选型

### 5.1 模型（**不要改**）

| 用途 | 模型 | 维度 | 说明 |
|---|---|---|---|
| Embedding | `BAAI/bge-m3` | **1024** | 🔴 **项目已锁定 1024 维**（`rag_contracts.EMBEDDING_DIM` —— ⚠️ 它是 `rag_contracts/chunk.py` 的**模块级常量**，**不是** `ContractChunk` 的类属性，写成 `ContractChunk.EMBEDDING_DIM` 会 `AttributeError`；另一处是 `RagSettings.vector_dim`）。**换模型改维度 = 全量重建索引**，非必要不做 |
| Reranker | `BAAI/bge-reranker-v2-m3` | — | `CG_RAG_RERANK_MODEL` 的默认值就是它 |

### 5.2 服务形态对比

| 形态 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **TEI**（HuggingFace Text Embeddings Inference） | 官方镜像；**专为 embedding/rerank 优化**；项目的 `CG_RAG_EMBED_PATH` 注释里就写着「TEI 用 `/embed`」 | 需自备模型权重（可挂卷缓存） | ✅ **自部署首选**（作者显然已为它预留配置） |
| Xinference | 一个服务同时提供 embedding + rerank + LLM | 镜像较大 | ✅ 想少起容器 |
| vLLM | 以 LLM 推理为主 | embedding 支持较新、rerank 弱 | 若同时要自部署 LLM |
| Ollama | 安装简单 | embedding 模型少、**rerank 支持弱** | 本地快速试验 |
| **云端 API**（OpenAI / 智谱 / DashScope 等） | **零部署成本，最快达标** | 依赖网络；演示现场若无网则不可用 | ✅ **开发期首选**（先用它把指标跑出来） |

> 💡 **推荐组合**：**开发期用云端 API 快速验证指标 → 演示期换 TEI 容器保证离线可跑**。
> 两者的接口口径一致（OpenAI 兼容 / TEI），**只改环境变量**。

## ⑥ 配置规格

### 6.1 切到真实语义服务（`.env.example` 补充块）

```dotenv
# =============================================================================
# 【推荐】切到真实语义服务（T-A5 / T-A6）
#   不切则默认 hash + noop：链路可跑通，但无语义能力，召回不达标
# =============================================================================
# ⚠️ 主力向量库是 Qdrant（2026-09-21 拍板，见 `1.RAG模块.md` §1.1.3）。
#    不要在这里填 milvus —— Milvus 只是备选适配器（P2），不是生产路径。
#    离线调试可整行注释掉（默认走 inmemory）。
CG_RAG_VECTOR_STORE=qdrant

# ---- Embedding ----
# hash=离线伪向量（默认/单测）；http=真实服务
CG_RAG_EMBED_MODE=http
CG_RAG_EMBED_BASE_URL=http://localhost:8080
# ⚠️ 路径按服务类型二选一：
#     TEI            → /embed
#     OpenAI 兼容    → /v1/embeddings
CG_RAG_EMBED_PATH=/embed
CG_RAG_EMBED_MODEL=BAAI/bge-m3
CG_RAG_EMBED_API_KEY=none
CG_RAG_EMBED_BATCH_SIZE=32
# ⚠️ 真实模型首次推理较慢，CPU 上建议放宽到 10000ms
CG_RAG_EMBED_TIMEOUT_MS=10000

# ---- Reranker ----
# noop=恒等透传（默认）；http=真实精排；local=已禁用（红线禁 torch，会回退 noop）
CG_RAG_RERANK_ENABLED=true
CG_RAG_RERANK_MODE=http
CG_RAG_RERANK_HTTP_URL=http://localhost:8081
CG_RAG_RERANK_PATH=/rerank
CG_RAG_RERANK_MODEL=BAAI/bge-reranker-v2-m3
CG_RAG_RERANK_API_KEY=none
CG_RAG_RERANK_TIMEOUT_MS=10000

# ---- 策略：BM25 已可用，可切混合检索 ----
CG_RAG_STRATEGY=HYBRID_RRF
```

> 🔴 **`CG_RAG_RERANK_MODE` 不要写 `local`**。
> `factory.build_reranker()` 对 `local` 会**直接回退 `NoopReranker` 并打 warning**（因为红线禁 torch）。
> 写了 `local` 会得到"看起来配了精排、实际没生效"的假象。

### 6.2 compose 服务定义（若选自部署）

```yaml
  # ---------------------------------------------------------------------------
  # 语义服务（T-A5 / T-A6 新增）
  #   TEI：embedding 用 /embed，rerank 用 /rerank（同一镜像两种用途）
  #   模型权重挂卷缓存，避免每次重建都重新下载
  # ---------------------------------------------------------------------------
  embeddings:
    image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.5
    command: ["--model-id", "BAAI/bge-m3", "--port", "80"]
    ports: ["8080:80"]
    volumes: ["teicache:/data"]
    # 有 GPU 时换 cpu-1.5 为对应 cuda 标签，并加 deploy.resources.reservations.devices

  reranker:
    image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.5
    command: ["--model-id", "BAAI/bge-reranker-v2-m3", "--port", "80"]
    ports: ["8081:80"]
    volumes: ["teicache:/data"]
```

`volumes:` 段追加 `teicache:`。

## ⑧ 阈值调参记录（**实测后回填**）

> 说明：`score_threshold` 与 `rerank_threshold` 的合理取值**高度依赖所用模型**，
> 换模型/换服务后必须重新标定。以下留空待实测填写。

| 配置项 | 默认值 | 实测建议值 | 依据 |
|---|---|---|---|
| `CG_RAG_SCORE_THRESHOLD` | `0.35` | ⬜ 待填 | 用 T-A8 的评测集扫阈值，取 F1 最优点 |
| `CG_RAG_RERANK_THRESHOLD` | `0.35` | ⬜ 待填 | 同上 |
| `CG_RAG_DENSE_TOP` | `20` | ⬜ 待填 | 增大可提升召回，但增加精排耗时 |
| `CG_RAG_SPARSE_TOP` | `20` | ⬜ 待填 | 同上 |
| `CG_RAG_RERANK_TOP_N` | `5` | ⬜ 待填 | 直接决定注入 Prompt 的条数（影响 Token 预算） |
| `CG_RAG_RRF_K` | `60` | `60` | 沿用前作，无充分理由不改 |

### 调参红线

🔴 **`scores.final` 的 clamp 语义不可改**（见 `1.RAG模块.md` §1.4.3）。
若为了让更多结果通过阈值而改用 `(x+1)/2` 线性映射，
**会把"无关文本"抬到 0.5，直接击穿阈值，使「缺失标准对照」信号失效** ——
即**废掉赛题要求的"缺失条款提醒"功能**。

**正确做法**：改 `score_threshold` 的取值，**不要改分数的映射方式**。

## ⑨ 换模型 = 重建索引（操作流程）

`ContractChunk.embedding_model` 字段**已存在**（契约里就有，用于识别旧索引）。

```
1. 确认新模型维度是否仍为 1024
   ├─ 是（如换 bge-large-zh 需改维度，注意） → 继续
   └─ 否 → 需同时改 CG_RAG_VECTOR_DIM，且【必须】重建索引与新 collection
2. 用新 collection 名（如 contract_clauses_bge_m3_v2）建库并全量写入
   ⚠️ 不要原地覆盖：旧索引要保留，便于双跑对比与回退
3. 双跑对比：同一批 query 在旧/新 collection 上的 Top-10 重合度 + 人工抽查
4. 达标后切换 CG_RAG_COLLECTION 指向新 collection
5. 保留旧 collection 至少一个迭代周期
```

> ⚠️ **不要原地 upsert 覆盖**：不同模型的向量在同一空间里不可比，
> 混写会让检索结果**静默变差**（不报错，只是变差），这是最难发现的一类故障。

## ⑩ 避坑清单

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | `CG_RAG_RERANK_MODE=local` | 静默回退 noop，精排**没生效**却以为配好了 | 用 `http`（`local` 因红线禁用，见 `0.§0.3`） |
| 2 | `CG_RAG_EMBED_PATH` 填错（TEI 写成 `/v1/embeddings`） | 404 → 降级 → 看起来"服务起了但没效果" | TEI 用 `/embed`，OpenAI 兼容用 `/v1/embeddings` |
| 3 | 超时太短（默认 3000ms） | CPU 上首次推理超时 → 降级 | 真实模型放宽到 **10000ms** |
| 4 | 只看"有结果"就认为精排生效 | 可能精排没生效但稠密路恰好够用 | **必须查日志 `retrieve.rerank` 的 `model` 字段 ≠ `noop`** |

| 6 | 换模型后原地 upsert 覆盖旧 collection | 向量空间混用，结果静默变差 | **新建 collection + 双跑 + 切换** |
| 7 | 假定有 GPU | CPU 上延迟超预期 | 先测 CPU 延迟；必要时减 `top_k` 或换更小模型 |
| 8 | 演示现场依赖云端 API 但无网络 | 现场演示失败 | **演示前切 TEI 本地容器**并预跑一次 |

### ⑪.1 ⚠️ 与 §②「不改代码」的差异（**已裁决**）

原文 §②/§③ 写「**不改 `HttpEmbedder` 的代码**（两者已实现且有测试）」「本任务几乎没有代码改动」。
**C3 组件卡**（`0.§0.1.4` 的组件层）却明确要求：`HttpEmbedder` 增 **维度校验 / 分批 / 空文本与超长的确定性处理**，
并新增 `provider_presets.py` + `factory.build_embedder()` 的预设补全。

**裁决**：采用**组件卡**（它是任务层的分解，且落点经 `1.RAG模块.md §1.5.1` 登记）。
理由是——「**不改代码**」这句是把"部署即可达标"的乐观估计写成了结论，而实测证明
**不改代码就不够**：`HttpEmbedder` 原来对空文本会发空 `input`（服务端 4xx）、
对维度不符直接抛错而无留痕、也没有 provider 端点表（用户要在 `.env` 里手抄 `path`/`model`，
正是 §⑩ 避坑 2/3 的成因）。原文保留，以本节为准。

### ⑪.2 §⑦.1 冒烟对比实测（**断言 1·2 已通过**）

环境：本机 **ollama 0.34.0 + `bge-m3:latest`（1024 维，CPU）**；向量库用 `qdrant`（`local_memory` 模式，
免得为一次冒烟起容器）。**未做** §⑦.1 里"云端 API"那条路（无 Key、且演示要离线）。

| # | 断言 | 改前（`hash` + `noop`） | 改后（`http` bge-m3） |
|---|---|---|---|
| 1 | 3 条查询全部 `returned > 0` | ❌ 2 / **0（EMPTY_RECALL）** / 2 | ✅ **3 / 3 / 3** |
| 2 | `top_score` 全部 `> 0.35` | ❌ 0.5017 / **0.3398** / 0.4896 | ✅ **0.8025 / 0.7365 / 0.7743** |
| 3 | `retrieve.rerank` 的 `model ≠ noop` | — | ✅ **`BAAI/bge-reranker-v2-m3`**（3 次调用，`pairs=20`，`dropped_count=17/19/18`）—— 由 **C4/T-A6** 补齐，见 §⑪.6 |
| 4 | 阶段耗时含 embed/dense/sparse/fusion/rerank | 部分（无 embed 真耗时） | ✅ **五阶段齐备** —— 但要注意冒烟脚本写死了 `DENSE_ONLY`（§⑪.6-③ 给出 HYBRID_RRF 下的实测键） |

| 6 | 离线基线未退化 | ✅ | ✅ 全量 `352 passed / 7 skipped / 1 failed`（那 1 条是**既有**的 OCR 超时用例，与本任务无关） |

**顺带取得的两条硬事实**（回填到 `1.C3` 卡片 §⑥）：

| 事实 | 实测值 |
|---|---|
| 语义区分度 | 近义条款余弦 **0.8513** vs 无关文本 **0.5396**（伪向量无此区分力） |
| CPU 推理延迟 | 冷启动 / 空闲后再加载 **≈ 34 ~ 41 s**；热态单条 **≈ 0.42 ~ 0.48 s**；批量 32 条 **≈ 43 s** |

### ⑪.3 ⚠️ §⑥.1 的 `CG_RAG_EMBED_TIMEOUT_MS=10000` **不够**

实测冷启动要 **34 ~ 41 s**（§⑩ 避坑 3 只提醒"放宽到 10000ms"）。按 10000ms 配会在**每次模型被卸载后**
稳定超时降级（现象是"服务明明是好的，检索却突然变差"）。**建议**：

- 演示/自部署走 ollama + CPU 时，`CG_RAG_EMBED_TIMEOUT_MS ≥ 60000`（本项目真实用例默认 120000，
  可用 `CG_RAG_TEST_EMBED_TIMEOUT_MS` 覆盖）；
- 生产建议换 **TEI**（GPU/批量优化）或云端 API，届时按 §⑥.1 原值即可。
> 本文件 §⑥.1 的示例值**保留原文**，以本条为修正。
