## ⑥ T-A2 · `factory.build_vector_store()` 新增分支

```python
def build_vector_store(settings: RagSettings) -> VectorStorePort:
    """按配置构造向量库。

    Args:
        settings: RAG 配置。

    Returns:
        VectorStorePort 实现。

    Raises:
        ValueError: `vector_store` 取值非法。
    """
    if settings.vector_store == "inmemory":
        return InMemoryVectorStore()
    if settings.vector_store == "qdrant":
        from .adapters import QdrantVectorStore  # 延迟导入：默认路径不加载 SDK

        return QdrantVectorStore(
            mode=settings.qdrant_mode,
            url=settings.qdrant_url,
            path=settings.qdrant_local_path,
            api_key=settings.qdrant_api_key,
            collection=settings.collection,
            timeout_s=settings.timeout_ms / 1000.0,
        )
    if settings.vector_store == "milvus":
        from .adapters import MilvusVectorStore  # 延迟导入：与 qdrant 分支风格一致

        return MilvusVectorStore(
            mode=settings.milvus_mode,
            uri=settings.milvus_uri,
            token=settings.milvus_token,
            db_name=settings.milvus_db_name,
            collection=settings.collection,          # 复用同一 collection 配置项
            timeout_s=settings.milvus_timeout_s,
        )
    raise ValueError(f"不支持的 vector_store：{settings.vector_store}")
```

**`adapters/__init__.py` 导出**（与 `QdrantVectorStore` 对称，加入 `__all__`）：

```python
from .milvus_store import MilvusVectorStore   # 注意：模块内延迟导入 pymilvus，此处 import 安全
```

> 理由是：即使模块内延迟导入 `pymilvus`，**包出口的急切导入**仍会把整个 `adapters` 的可用性
> 绑死在"文件必须存在且可导入"上，与"缺 SDK 时默认路径完好"的离线红线相冲突。
> 断言 6「`from rag_core.adapters import MilvusVectorStore` 成功」在 PEP 562 下**同样成立**

## ⑧ T-A7 · 8 个失效配置项接线（**本文件第二个重点**）

### 问题现状

`RagSettings` 声明了 **36 个字段**（实测 `len(RagSettings.model_fields) == 36`；⚠️ T-A7 删掉 `log_level` 后为 **35**），
但 `factory.build_service_from_settings()` 只消费其中 `dense_top` / `sparse_top` / `rrf_k` /
`max_context_tokens` / `timeout_ms`（外加 `bm25_*` / `embed_*` / `vector_store` /
`rerank_enabled` / `rerank_mode`）。以下 **8 项**无人消费：

> 📌 **判定口径（先明确，否则会数错）**：`service.py` **一处都不读配置**
> （实测：在 `service.py` 里搜 `settings` / `config` = **0 命中**），
> 所以此处「有消费者」= **`factory.py` 读取过**。
> `strategy` / `score_threshold` 目前只在冒烟脚本与单测里被读到，**生产路径上仍是死配置** —— 这正是本任务要修的。

```text
strategy          CG_RAG_STRATEGY           ← 改它完全无效（请求侧默认值才是实际值）
score_threshold   CG_RAG_SCORE_THRESHOLD    ← 阈值实际由请求侧决定
rerank_threshold  CG_RAG_RERANK_THRESHOLD   ← 无消费者
rerank_top_n      CG_RAG_RERANK_TOP_N       ← 无消费者（请求侧有同名参数）
log_level         CG_RAG_LOG_LEVEL          ← 无消费者（logger.py 直接读环境变量，本字段是重复声明）
max_retries       CG_RAG_MAX_RETRIES        ← 无消费者
max_query_chars   CG_RAG_MAX_QUERY_CHARS    ← 无消费者
cache_ttl_s       CG_RAG_CACHE_TTL_S        ← 无消费者
```

### 影响（为什么必须修）

| 项 | 影响 |
|---|---|
| `strategy` | `CG_RAG_STRATEGY` 目前是**死配置**。`.env.example` 里写着「T03 完成后请改为 HYBRID_RRF」，但改了**不会有任何效果** |
| `max_retries` / `max_query_chars` | 🔴 **Agent 层「三道防线」（超长拦截 / 超时重试 / 空召回降级）依赖这两项，但引擎不存在** → 防线目前是纸面的 |
| `log_level` | **重复声明**：日志级别实际由 `cg_observability/logger.py` 直接读环境变量 `CG_RAG_LOG_LEVEL`（`os.environ.get`）。改 `RagSettings.log_level` **不会有任何效果** |
| `score_threshold` | 服务端默认值不生效，无法做「不传参也有合理默认」的灰度 |
| `cache_ttl_s` | 无缓存实现（可作为**未实现标记**显式登记，而非静默忽略） |

### 接线规格

| 配置项 | 落地方式 | 落点 |
|---|---|---|
| `strategy` | `build_service_from_settings()` 传入 `RAGService`，作为**请求未显式指定时的默认策略** | `factory.py` + `service.py` |
| `score_threshold` | 同上，作为请求默认阈值 | `factory.py` + `service.py` |
| `rerank_top_n` | 传给 `RAGService` 的 `_rerank_top_n`；请求侧显式传值时请求优先 | `service.py` |
| `rerank_threshold` | 精排后阈值（与 `score_threshold` 分工：前者作用于 rerank 分，后者作用于 final） | `service.py` |
| `timeout_ms` | ⚠️ **它已有消费者，别再当成死配置**：`factory.build_vector_store()` 用它设 Qdrant 客户端超时（`timeout_s=settings.timeout_ms/1000`）。本任务**追加**语义：同时作为 `retrieve()` 的整体超时预算（契约里已有该语义） | `factory.py`（已有）+ `service.py`（新增） |
| `log_level` | 二选一：**①（推荐）删除该字段** —— `logger.py` 已直接读环境变量，删掉即消除「同一配置两个入口」；② 改 `logger.py` 改为消费本字段 | `config.py`（选①）／`cg_observability/logger.py`（选②） |
| `max_retries` | **不在 `rag-core` 实现**（`rag-core` 不该管重试策略）→ 交由 Agent 工具层的 `_with_timeout_retry` 消费 | `ai_engine/agents/tools.py`（T-B4） |
| `max_query_chars` | 同上，**工具层防线 1** 消费 | `ai_engine/agents/tools.py`（T-B4） |
| `cache_ttl_s` | 无实现 → **显式标注为「已登记未实现」**，在 `config.py` 的 field description 里写清，避免再次误判 | `config.py` |

> 🔴 **重要判断**：`max_retries` / `max_query_chars` **不应在 `rag-core` 里实现**。
> 它们的语义是「Agent 工具的调用策略」，属于上层关注点。
> 把它们塞进 `rag-core` 会违反分层（`rag-core` 不知道自己被谁调用）。
> **本任务只负责让它们"有明确的消费者归属"**，真正消费在 T-B4。

### 实现规范（`overrides` 反射的坑）

`build_service_from_settings(**overrides)` 通过 `f"_{key}"` 反射设置私有字段。
**新增可覆盖字段必须命名为 `_<同名>`**，否则 overrides 静默失效：

| 配置项 | 必须对应的私有字段名 |
|---|---|
| `strategy` | `self._default_strategy`（命名为 `_default_strategy`，则 overrides 键为 `default_strategy`） |
| `score_threshold` | `self._default_score_threshold` |
| `rerank_top_n` | `self._rerank_top_n` |
| `rerank_threshold` | `self._rerank_threshold` |

> ⚠️ **默认策略与请求默认值的关系**：
> `RAGQueryRequest.strategy` 的默认值是 `HYBRID_RRF`（"能力声明"），
> `CG_RAG_STRATEGY` 默认 `DENSE_ONLY`（"当前实际启用"）—— **二者刻意的差异**（源码有说明）。
> 接线时**不要把这个差异"修掉"**，否则离线默认路径会因为 BM25 不可用而反复降级告警。
> 正确做法：**配置值作为服务级兜底**，仅当调用方未显式传 `strategy` 时生效。
