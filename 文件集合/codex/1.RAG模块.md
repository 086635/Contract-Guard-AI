## 1.1 模块目标

在**不破坏现有契约与编排**的前提下，把 RAG 从「机制正确但语义贫弱」推进到「**语义可用、指标可量测、架构可扩展**」。

### 1.1.1 对应赛题硬指标

| 赛题指标 | 阈值 | RAG 模块的支撑方式 |
|---|---|---|
| 风险条款识别召回率 / 精准度 | ≥ 75% / 75% | 混合检索召回 + 精排质量（**本模块直接负责**） |
| 标准条款比对 + 缺失条款提醒 | 必须 | 用 `EMPTY_RECALL` / 低分命中作为「缺失标准对照」信号（机制已存在） |
| 报告含原文位置 | 必须 | `ContractChunk.bbox` → `RetrievedDoc.bbox` 的溯源链路（契约已通，坐标由 OCR 模块供给） |
| 报告含法律依据 | 必须 | `CitationOut` → `EnhancedRiskItem.citations`（契约已通） |

### 1.1.2 本模块的四个关键词

```
补语义   —— 接入真实 embedding 与 reranker（当前是哈希伪向量 + noop，故召回不达标）
稳主库   —— Qdrant 保持主力（与现行项目配置一致），不迁移、不动默认路径
展扩展   —— Milvus 作为【备选适配器】（P2），证明 Ports & Adapters 的可插拔能力
可量测   —— 建评测集与 Recall@K 脚本（没有度量就没有调参，这是达标的先决条件）
```

### 1.1.3 向量库策略（**已拍板 · 2026-09-21**）

| 角色 | 实现 | 状态 | 说明 |
|---|---|---|---|
| **主力 / 生产** | `QdrantVectorStore` | ✅ 已实现、已测试、已接线 | 与 `RAG_MODULE_DESIGN.md` §1.3 的既有结论**一致**，不改默认路径 |
| **离线 / 单测** | `InMemoryVectorStore` | ✅ 已实现 | 零依赖，兑现「默认路径离线可跑」红线 |
| **备选 / 可扩展性展示** | `MilvusVectorStore` | ⏳ P2 待做（见 `1-2`） | 证明「换库 = 加文件 + 加分支」，业务层零改动 |
| 数据迁移 | — | **不需要**（T-A10 取消） | 生产库**不切换**，故无迁移需求 |

**为什么这样定**（论证详见 §1.7.1）：

1. **决定分数的是语义与度量，不是向量库** —— 瓶颈在 `HashEmbedder` + `NoopReranker`，换库对召回率的边际收益 ≈ 0。
2. **开发机是 Windows，而 Milvus Lite 官方不支持 Windows** → Milvus 只能走 Docker 三件套（etcd + MinIO + Milvus），冷启动 30~60s；Qdrant 是单容器、秒级。
3. **演示可靠性** —— 单容器 vs 三件套，活动部件越少越好。
4. **规模用不上** —— 本项目切片量级 10⁴~10⁵，Qdrant 单容器可覆盖到百万级；Milvus 的十亿级/分布式优势在此**无收益**。

> 🔴 **一句话红线**：**默认路径永远是 `inmemory`（离线）或 `qdrant`（生产）**。
> Milvus **不得**成为任何默认值，也**不得**成为关键路径上的依赖。

## 1.4 端到端数据流

### 1.4.1 离线建库（写入）

```
语料(JSONL / 解析层输出)
   → SimpleChunker.chunk()            产出 ContractChunk[]        [已有的]
   → EmbedderPort.embed_batch()       产出 vector[][]（1024 维）   [T-A5 换成真模型]
   → VectorStorePort.upsert()         写入向量库                  [T-A1 支持 Milvus]
   → SparseStorePort.upsert()         写入 BM25 倒排/正排表        [已有]
```

> ⚠️ **两路索引必须用同一套 `chunk_id`**。
> `ContractChunk.chunk_id` 由 `make_chunk_id(doc_id, section_id, slice_idx)` 用 **uuid5 确定性生成**，
> 这是两路可对齐的前提（源码已保证，勿改）。

### 1.4.2 在线检索（读取）

```
RAGService.retrieve(request)
  ├─ 策略判定：strategy != DENSE_ONLY 且 sparse_store 为 None → 降级 DENSE_ONLY + warning
  ├─ embed     : embedder.embed_one(query)                → 查询向量 + token 计量
  ├─ dense     : vector_store.search(vec, dense_top, filters)   → VectorHit[]
  ├─ sparse    : sparse_store.search(query, sparse_top)    → SparseHit[]     [T-A0-2 修复]
  ├─ fusion    : rrf_fuse([dense_ranked, sparse_ranked], k=rrf_k)
  ├─ rerank    : reranker.rerank(query, texts, base_scores) [T-A6 换成 HTTP 精排]
  ├─ 阈值过滤  : final >= score_threshold  否则 → EMPTY_RECALL 降级
  ├─ build     : ContextBuilder.build(docs, max_context_tokens)
  └─ 返回 RAGQueryResponse（含 degraded / fallback_reason / citations / token_usage）
```

**红线**：`retrieve()` **永不抛异常**。任何失败路径 → `_degraded()` 响应。

### 1.4.3 分数口径（**改动阈值前必须理解**）

| 字段 | 含义 | 范围 |
|---|---|---|
| `scores.dense` | 稠密路**原始余弦相似度**（保留供调试） | `[-1, 1]` |
| `scores.sparse` | BM25 原始分（未归一，量纲与余弦不可比） | `[0, +∞)` |
| `scores.fused` | RRF 融合分 `Σ 1/(k+rank)`，**非归一** | `(0,1)` 小数 |
| `scores.rerank` | 精排分 | `[0,1]` |
| `scores.final` | **用于与 `score_threshold` 比较** | `[0,1]` |

🔴 **`final` 用 clamp 而非 `(x+1)/2` 线性映射**（源码注释已说明）：
后者会把"无关文本"（余弦≈0）抬到 0.5，**直接击穿 0.35 阈值，使"缺失标准对照"信号失效**。
**改这里等于废掉缺失检测功能。**

### 1.7.1 D1 终裁：Qdrant 主力 + Milvus 备选（**2026-09-21 拍板**）

#### 裁决结论

| 项 | 裁决 |
|---|---|
| 主向量库 | **Qdrant**（保持现行配置，不改默认路径） |
| 离线/单测 | **InMemoryVectorStore**（零依赖，红线不变） |
| Milvus 定位 | **备选适配器**，用于**展示可扩展性**；P2，不阻塞达标 |
| 数据迁移 | **不做**（生产库不切换）→ T-A10 取消 |
| 默认值红线 | `CG_RAG_VECTOR_STORE` 的**代码默认仍是 `inmemory`**；生产/演示在 `.env` 显式设 `qdrant`。**Milvus 不得成为任何默认值** |

#### 与既有设计文档的关系：**由「冲突」转为「一致」**

初版本文曾把「以 Milvus 为核心」记为与既有决策的冲突。**现在这个冲突已消解**：

`文件集合/report/RAG_MODULE_DESIGN.md` §1.3 的既有结论原文是：

> 「换 Milvus = 重写索引建表、payload schema、过滤 DSL、运维体系，**代价 ≥ 2 人周且无业务收益**」
> 「**结论建议**：Phase 3 不切 Milvus。若未来确有亿级向量需求，再按上表执行，届时只需新增一个 Adapter + 改 DI 工厂。」

**本次裁决与该结论一致**，无需回写该文档的结论，只需**追加一段决策记录**（见 `RAG_MODULE_DESIGN.md` 顶部的纠偏声明）。

#### 为什么不是「以 Milvus 为核心」（复核后的四条硬理由）

| # | 理由 | 依据 |
|---|---|---|
| 1 | **决定分数的是语义与度量，不是向量库**。赛题硬指标是「风险条款识别召回率 ≥75%」，瓶颈在 `HashEmbedder`（伪向量）+ `NoopReranker`（无精排）。换库对召回率边际收益 ≈ 0 | 实测：冒烟 3 条查询 1 条 `EMPTY_RECALL`，原因为默认非语义向量 |
| 2 | **开发机是 Windows，Milvus Lite 官方支持矩阵不含 Windows** → 只能走 Docker 三件套（etcd + MinIO + Milvus），冷启动 30~60s；Qdrant 单容器、秒级 | 见 `1-4` §⑦ |
| 3 | **演示可靠性**：单容器 vs 三件套，活动部件越少越好；答辩现场是"跑一遍"的场景 | 见 `1-4` §⑥ |
| 4 | **规模用不上**：本项目切片量级 10⁴~10⁵（民法典 ~1260 条 + 标准范本 + 单次上传合同），Qdrant 单容器覆盖到百万级无压力。Milvus 的十亿级/分布式优势在此**无收益** | `vector_dim=1024`，`collection=contract_clauses` |

> 💡 **当初为什么会被高估**：旧结论估的是「重写索引建表 / payload schema / 过滤 DSL / 运维体系 ≈ 2 人周」，
> 但 `VectorStorePort` 抽象层已经落地，业务层 `service.py` **一行都不用改**，
> 实际体量 ≈ 250~320 行 + 25 行装配（`1-2`）。**代码代价被高估了，运维代价仍然成立** ——
> 而运维代价正是本裁决把它降为 P2 的理由。

#### 那为什么还要做 Milvus？（**保留 B 组的意义**）

不是技术必需，而是**架构能力的证明**：

1. **它是 Ports & Adapters 的验收证据** —— 能"加文件 + 加分支"就换掉向量库，且 `service.py` / `rag_contracts` 零改动，这本身就是交付物的一部分。
2. **它是可逆性的保险** —— 若未来法规库真的涨到千万级，切换成本已被证明为 ~2 人日而非 2 人周。
3. **它不污染主路径** —— 独立 collection、`skipif` 集成测试、可选 compose profile，**离线基线不受任何影响**。

> 🔴 **纪律**：B 组**任何一项都不得让 A 组的测试基线出现退化**，
> 也不得让默认路径（`inmemory`）多出任何 import 依赖。这是 `0.§0.9` DoD 的硬要求。

### 1.7.2 D4 终裁：统一 HTTP 接口 + 配置区分多端（**2026-09-21 拍板**）

| 子项 | 终裁 | 对代码的影响 |
|---|---|---|
| **D4-a** 服务形态 | **统一走 HTTP 接口**：开发期用本地 **ollama**；云端模型与本地模型**只靠配置区分** | **零代码改动**：`HttpEmbedder` / `HttpReranker` 已实现且已有测试，只改 `CG_RAG_EMBED_BASE_URL` / `CG_RAG_EMBED_MODEL` / `CG_RAG_EMBED_API_KEY` 与 `CG_RAG_RERANK_HTTP_URL` / `CG_RAG_RERANK_PATH` |
| **D4-b** GPU 策略 | 有 GPU（RTX 5060 8 GB）但**大数据量不走本地计算** → 同样走「统一接口多端调用」 | ① **不需要**在 compose 里硬绑 GPU；② `embed_mode` / `rerank_mode` 的**默认值必须保持离线**（`hash` / `noop`，红线）；③ ollama 只作为**可选切换**（实测服务未启动，不能设为默认） |
| **D4-c** 换模型 = 重建索引 | **是**，流程固化为四步 | ① 读 `CG_RAG_EMBED_MODEL` + `CG_RAG_VECTOR_DIM`；② 扫 `chunk.embedding_model` ≠ 当前值的存量切片；③ 用新 collection 名 `<collection>_<model_slug>` 重建（旧库保留只读）；④ 冒烟 3 条查询确认 `EMPTY_RECALL` 消失后切默认名。⚠️ 维度变化视为**破坏性变更**（须先改 `rag_contracts.EMBEDDING_DIM` 再全量重建） |

> 🔬 **实测依据（2026-09-21）**：ollama **客户端 0.34.0 已装、服务未启动**（`GET /api/tags` 无响应）；
> 因此 `.env` 必须保留离线默认，ollama 只以**注释形式**给在 `.env.example` 里（见该文件）。
>
> 🔴 **与 2-6/2-5 的关系**：`T-A5/A6` 是 **Agent 线三道防线的前提**之一（`max_query_chars` / `max_retries` 由工具层消费），
> 本裁决落地后 RAG 与 Agent 两条线都能继续推进。
