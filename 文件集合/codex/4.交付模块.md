# 4 · 交付（端到端收口）

> 所属模块序号：4 · 交付　公共规范见 `0.施工标准与定义归属.md`（下称“标准”）
> 规划文档：`项目路径规划2.0.md`（L4 性质，本模块的执行总路线；本文是其**施工层总纲**）

## 4.1 模块目标

把已闭合的 RAG / Agent / OCR 三条主线，与已冻结的 API 契约（`openapi.yaml`）、数据契约（`data_scheme.md`）接成**一个可运行、可演示、可交付的完整系统**：数据持久化、网关真实化、报告生成、端到端联调、前端渲染。

## 4.3 分层架构

```text
Frontend ──HTTP/SSE──> API Gateway ──> Service ──> DAL ──> PostgreSQL
                                 └──> Celery/Redis ──> Worker ──> RAG/Agent/OCR
Worker ──> MinIO（文件/工件）＋ Qdrant/Milvus（向量）
```

三存储分工：PostgreSQL=状态机/结构化结果/配置/反馈；Qdrant/Milvus=向量+检索 payload；MinIO=原始文件/解析工件/报告 DOCX。

## 4.4 端到端数据流

```text
上传：presign → MinIO 直传 → commit 建 contracts → 派发 parse_doc
解析：worker 读 MinIO → OCR/Layout → 切片+向量入 Qdrant → 写 contract_elements
审核：派发 run_audit → audit_graph → 写 audit_risks/conflicts → SSE 实时推
报告：派发 gen_report → DOCX → MinIO → 写 audit_reports → 返回 downloadUrl
渲染：前端 GET risks/conflicts/seals/report
```

## 4.8 与其他模块的边界

- 依赖 1/2/3 的**产物**（`rag_core`、`ai_engine`、`doc_processor`），**不改**其内部实现；仅通过公开入口消费（`build_service_from_settings`、`RagTool`、`build_parse_pipeline`）。
- 契约字段/枚举/端点一律以 `openapi.yaml` / `data_scheme.md` / `rag_contracts` 为准，本模块只做**持久化与接线**，不新增字段定义（新增字段须回 `packages/schema/openapi.yaml` 再 `pnpm gen`）。
- 生成物 `schemas.py` / `types.ts` / `zod.ts` 禁止手改。
- worker 只通过 Celery 任务与结果和 gateway 交互，不 import `app.*`；报告元数据落库由 gateway 负责。
