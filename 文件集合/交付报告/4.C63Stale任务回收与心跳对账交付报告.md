## 1. 任务目标

C63 让「worker 崩溃/失联」不再表现为「任务永远 RUNNING」：

1. worker 上报心跳；网关侧对账回写 `last_heartbeat_at`。
2. reconciler 扫描超时/失联任务：可重试则重派，超限则标 FAILED。
3. 记录 reconcile 审计与 traceId。
4. 提供可定时执行的 CLI/Beat 入口。

## 2. 实现说明

### 2.1 心跳：worker 打点、网关对账（两边契约一致）

```text
worker/progress.py       每次 _emit → publish(task_progress:{id}) + set(task_heartbeat:{id}, ex=CG_TASK_HEARTBEAT_TTL_S)
                         （worker 只写 Redis，不写业务 DB；TTL 必须 < stale 阈值）
cg_observability          task_heartbeat_key()   ← 键名唯一定处（worker 与网关共用）
app/services/progress.py  RedisProgressBroker.heartbeat_seen(task_id)  ← 只读存在性，Redis 故障返回 False（保守）
app/db/repository         TaskRepository.heartbeat(task_id, at)        ← 网关把存活事实回写 DB
```

**为什么分开**：进度是**事件流**（可能长时间没有新阶段），心跳是**存活标记**；只有心跳缺失才说明失联。
判定规则（§⑨-1）：只看 `last_heartbeat_at`（无心跳时回退 `updated_at`），**绝不看 `created_at`**
（长任务可能创建很久但一直在推进）。

### 2.2 reconciler：`app/services/task_reconciler.py`（新建）

```text
TaskReconciler.sweep(now=None) -> ReconcileReport{scanned,retried,failed,ignored,traceId,details}
  ① list_stale(stale_before, lock_expired_before)   # 非终态 + 心跳过期 + 锁空闲/过期
  ② heartbeat_seen(celery_task_id)  ── 存活 → heartbeat() 回写 DB，ignored+1（不派发）
  ③ claim(task_id, now, lock_expired_before)  ── 原子抢锁；抢不到 → ignored+1（并发 sweep 不双派）
  ④ 可重放 + can_retry → record_attempt()（attempt+1/errorCode/nextRetryAt/刷新心跳/释放锁）
                        → dispatch(task_id=f"reconcile-{task_id}-{attempt}") → attach_celery_task_id()
  ⑤ 否则 → mark_failed(errorCode) + 审计
```

- **阈值**：`CG_TASK_STALE_AFTER_S`（默认 300s）、`CG_TASK_LOCK_TIMEOUT_S`（默认 120s）。
- **UTC 且显式**：`sweep()` 拒绝 naive `datetime`（阈值必须基于明确时区）。
- **有限重试**：复用 C62 的 `TaskRecord.can_retry` / `retry_delay_seconds`（指数退避 5→300s 封顶）。
- **不伪造输入**：`PARSE_DOC` / `SCAN_UPLOAD` / `CONVERT_DOC` 的参数可从合同行重建（复用
  `ContractProjector._file_type` 与 C59 的 `convert_doc(contract_id, source_key)` 签名）；
  `RUN_AUDIT` / `GEN_REPORT` / `REWRITE` 的入参是**业务载荷**，行里没有快照 →
  收敛为终态 `RECONCILE_UNSUPPORTED_KIND` + 审计，交人工重触发（**不猜参数**）。
- **审计**：每次收敛写一条 `TASK_RECOVERED` 事件（`resource_type="TASK"`，metadata 只含任务元信息：
  contractId/taskType/errorCode/reconcile/attemptCount/maxAttempts），并带本次 sweep 的 traceId。

### 2.3 仓储支撑（`app/db/repository/contract.py`）

```text
TaskRepository.list_stale(stale_before, lock_expired_before, limit=200)
TaskRepository.heartbeat(task_id, at)
TaskRepository.claim(task_id, now, lock_expired_before) -> bool   # 原子条件 UPDATE
TaskRepository.record_attempt(task_id, error_code, next_retry_at, at)
```

`claim()` 的 WHERE 条件是「仍 RUNNING + 锁空闲/过期」，因此**同一行在并发 sweep 下只有一次能拿到**；
`record_attempt()` 刷新 `last_heartbeat_at` 并释放锁，重试窗口从本次重新起算，避免同一 stale 窗口被反复派发。

### 2.4 CLI：`scripts/reconcile_tasks.py`（新建）

```text
python scripts/reconcile_tasks.py --stale-after 300 --lock-timeout 120
输出：{"traceId":..., "scanned":..., "retried":..., "failed":..., "ignored":..., "details":[...]}
退出码：0=无终态失败；1=有任务被判 FAILED（便于 cron 告警）；2=参数/环境错误
```

定时编排（cron / Celery Beat / compose 服务）属 **C67**（生产 profile 与运维）。

## 7. 边界与后续

### 边界声明

- **不把崩溃任务永久留 RUNNING**：超限或不可重放一律终态 FAILED + errorCode + 审计；
- **不重复派发已终态任务**：SQL 过滤 + reconciler 内二次防御 + `claim()` 只认 RUNNING；
- **不依赖单个进程内存状态**：状态全部来自 `audit_tasks` 行，Redis 仅作存活证据（只读）；
- **不新增第二套任务扫描器**：只有 `TaskReconciler` 一个入口，CLI 只是它的薄包装；
- **不伪造派发输入**：业务载荷型任务不猜参数（见 §2.2）。

### 三处需知晓的决策

1. **落点扩展（4 个文件）**：`app/services/ports.py`、`app/services/progress.py`、
   `packages/cg-observability/{progress.py,__init__.py}` 不在本卡 ④ 清单内。理由：
   worker 与网关必须共用**同一个心跳键名**（唯一定处，避免两处字面量漂移），
   而网关读 Redis 必须走适配器（`app/` 下只有 `services/progress.py` 允许 import redis，
   由 `test_adapters_are_only_modules_importing_external_sdks` 守卫）。
2. **不可重放任务的收敛语义**：`RUN_AUDIT`/`GEN_REPORT`/`REWRITE` 的入参是业务载荷，
   任务行里没有快照 → 直接终态失败（`RECONCILE_UNSUPPORTED_KIND`）而不是盲目重派。
   若要支持重放，需要给任务行加参数快照（属数据模型变更，应新开卡片）。
3. **`TASK_RECOVERED` 动作的查询面**：`AuditAction` 模型里已有该值（写库 CHECK 也包含），
   但 OpenAPI 的 `AuditAction` 枚举未同步该值 → `GET /audit/events?action=TASK_RECOVERED`
   会被 422 拒绝（**既有文档/代码漂移**，非本卡引入）。修它要动 OpenAPI 枚举 + 生成物，
   建议随 C74/T-D7-10 收口。
