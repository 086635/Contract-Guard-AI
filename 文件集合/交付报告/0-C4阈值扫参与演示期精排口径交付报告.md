## 3. 结论与建议值

**建议：`score_threshold` / `rerank_threshold` / `dense_top` / `sparse_top` / `rerank_top_n` 全部维持默认**
（`0.35` / `0.35` / `20` / `20` / `5`）。逐条依据见 `1-6 §⑧`，要点：

- **`score_threshold`**：三点指标逐字相同；降到 `0.30` **救不回**那 4 条空召回 ——
  它们的最佳精排分本就在 `0.30` 之下，是**语料确无对应条款**的真信号（不是阈值把结果卡掉了）。升到 `0.40` 无可测增益。
- **`rerank_threshold`**：生效口径是 `max(score_threshold, rerank_threshold)`（`service.py:575`）——
  低于 `score_threshold` 时**恒不生效**（第 4 点与第 1 点指标逐字相同即证）。
- **`dense_top` / `sparse_top`**：`20→30` 指标逐字不变，但融合候选 **29.2（28–33）→ 42.2（39–46）**、
  精排对数 **+44%** —— 在精排 3.3 s/次的前提下是**纯亏**。
- **`rerank_top_n`**：`5→8→10` 连 **Recall@10 都不变** → 多留的候选里没有 gold，只增 Prompt Token 预算。

> 🎯 **平台期结论**：这 5 个旋钮**都拧不动召回**。剩下的 4 条空召回是**语料层缺失**，
> 要提升只能扩语料 / 换更强的召回模型，**不是调阈值**（这也正好保住了「缺失标准对照」信号）。

## 4. 演示期精排耗时口径（**含一条运维红线**）

**测量方式**：走产品装配入口 `build_service_from_settings()`，取 `RAGResponse.stage_latency_ms["rerank"]`；
语料 `eval_corpus.jsonl`（121 切片），gold 前 12 条查询，`pairs` 28–33。

| 指标 | 实测 |
|---|---|
| `retrieve.rerank` 单次 | 中位 **3319.5 ms** · P95 **3698 ms** · min 2310 / max 3995（n=12） |
| 整次 `retrieve`（`took_ms`） | 中位 **3539 ms** · min 2501 / max 4235 |
| 对照：`1-6`/本卡原标称"热态 top-20 ≈ **1.06 s**" | 本机实测**慢 3 倍以上**（机器常年跑 WPS/微信/钉钉/Excel）—— 属负载差异，**不是回归** |

### 🔴 默认 `rerank_timeout_ms=3000` 在本机不够

精排中位 **3.32 s 已超 3 s**。实测按默认 `3000` 跑完整评测时，**大量查询的精排被判失败并静默降级**
（`stage=retrieve.degrade, fallback_reason=RERANK_FAILED`），此时 `final` 退回 clamp 后的余弦分。

⚠️ **该降级态下 Recall@5 反而"升到 1.000"** —— 因为它**换了一套打分口径**，
**绝不可误读为调参收益**（这正是本卡差点踩进去的坑）。

**操作要求（已写进 `1-6 §⑧`）**
1. 演示前**必须显式调大** `CG_RAG_RERANK_TIMEOUT_MS`（本轮扫参统一 `60000`）；
2. 耗时 **> 3 s** → 按 `0-C4 §⑥` 口径，演示说明须标注 **"CPU 推理"**；
3. 耗时随负载波动大（同日两次实测 **2.3–4.0 s** 与 **6.3–10.0 s**）→ 演示前先跑一次 `phase1_smoke.py` 确认。
