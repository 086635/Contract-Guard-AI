## 1. 任务目标

C29 解决前端所有 HTTP 请求的错误归一化问题：

```text
后端错误体
  { code, traceId, serverTime, message?, detail? }
        ↓
Axios error interceptor
        ↓
Error.message = message ?? detail
Error.context.traceId = traceId
error.response.status 保持原始 HTTP status
```

目标不是改业务端点，而是让后续 C30~C35 在 SSE 断线、上传失败、报告失败、反馈/设置请求失败时收到稳定、可读且可诊断的错误对象。

## 3. 实现说明

### 3.1 错误体类型守卫

新增内部类型：

```ts
type ErrorPayload = {
  code?: string;
  traceId?: string;
  serverTime?: string;
  message?: string;
  detail?: string;
};
```

通过 `normalizeErrorPayload()` 读取未知响应体，所有字段都经过 `typeof string` 和 `trim()` 非空判断，不假定字段存在。

### 3.2 错误消息优先级

```ts
const userMessage = payload?.message ?? payload?.detail;
if (userMessage) error.message = userMessage;
```

行为：

- `message` 非空：使用 `message`；
- 仅有 `detail`：使用 `detail`；
- 两者都没有：保留 Axios 原始 `error.message`。

### 3.3 traceId 与状态码

- `traceId` 存在时使用非枚举属性挂到 Axios error；
- DEV 环境日志输出 `[api] <traceId> <message-or-detail>`；
- 原始 HTTP 状态码仍保留在 `error.response.status`；
- 网络错误/超时没有 response，直接 reject，不生成伪业务错误。
