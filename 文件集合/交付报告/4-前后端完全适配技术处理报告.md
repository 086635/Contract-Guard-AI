## 2. 问题矩阵

### 2.1 P0：阻断真实业务闭环

#### P0-1 网关任务 ID 与 Celery task ID 不一致

**现象**：

上传和报告接口返回的是 `audit_tasks.id`，但 `TaskService` 查询 Celery 状态时传入同一个网关任务 UUID。真正保存在 `audit_tasks.celery_task_id` 的 Celery ID 没有被使用。

**影响**：

- `GET /tasks/{taskId}` 永远只读到数据库初始状态。
- 上传和报告任务会长期显示 `RUNNING`。
- Worker 已经完成，前端仍无法进入可靠的 DONE 状态。

**证据**：

- `apps/api-gateway/app/services/task_service.py`
- `apps/api-gateway/app/db/repository/contract.py`
- `apps/api-gateway/app/services/contract_service.py`
- `apps/api-gateway/app/services/report_service.py`

**处置**：

- 先创建网关任务 UUID。
- 该 UUID 同时作为 `audit_tasks.id` 和 `celery_task_id`。
- `send_task(..., task_id=gateway_task_id)` 显式指定 Celery task id。
- `TaskService` 必须使用 `record.celery_task_id` 查询任务快照。

#### P0-2 Worker 没有发布 Redis 进度

**现象**：

Worker 只调用 Celery `update_state`，网关 SSE 订阅的是 Redis Pub/Sub `task_progress:{task_id}`。

**影响**：

- SSE 首包后不会收到后续阶段。
- 前端进度条不会推进。
- 断线轮询兜底也只有在 SSE 连接报错时才触发，不能覆盖“连接存在但无消息”的情况。

**证据**：

- `apps/async-worker/worker/progress.py`
- `apps/api-gateway/app/services/progress.py`
- `apps/api-gateway/app/services/task_service.py`

**处置**：

- 进度上报器同时执行 Celery `update_state` 和 Redis `publish`。
- channel 固定为 `task_progress:{task_id}`。
- 发布失败只告警，不改变任务业务结果。
- DONE / FAILED 后必须发布终态。

#### P0-3 前端监听了错误的 SSE 事件类型

**现象**：

后端通过 `format_sse()` 发送：

```text
event: progress
data: {...}
```

前端使用：

```ts
source.onmessage = ...
```

浏览器只有收到默认 message 事件时才触发 `onmessage`，命名事件必须用 `addEventListener("progress", ...)`。

**影响**：

- 即使后端开始发布，前端仍收不到进度。
- 上传和报告页可能永久停在准备状态。

**处置**：

- `taskApi.subscribe()` 改为监听 `progress` 命名事件。
- 终态 DONE / FAILED 后关闭连接。
- `onerror` 后执行 2 秒间隔轮询，并在 DONE / FAILED 时停止。

#### P0-4 解析结果没有落库

**现象**：

`parse_doc` 的文档明确写明不写数据库，只写 JSON 工件并返回 payload。

**影响**：

- 合同状态不会从 `PARSING` 推进。
- `GET /contracts/{id}/elements` 永远读不到真实抽取结果。
- 审核页无法展示真实要素、印章或条款。

**处置**：

- T-D6 增加 Worker 持久化桥。
- 解析完成后批量写入抽取要素与印章结果。
- 合同状态更新为 `PENDING_REVIEW`。

#### P0-5 自动审核没有接线

**现象**：

代码中只定义了 `TaskKind.RUN_AUDIT` 和 `run_audit_task`，没有从解析完成点自动派发或调用审核。

**影响**：

- 风险、矛盾、健康分不会产生。
- 审核工作台只能看到空结果。
- 报告任务没有真实审核数据可读。

**处置**：

- 从 `run_audit_task` 中抽出可复用核心函数。
- T-D6 的单流水线在解析和落库后调用该核心函数。
- 独立 `run_audit` Celery task 保留，供测试、人工重跑和后续异步拆分。

#### P0-6 报告生成仍是占位实现

**现象**：

- `gen_report_task` 直接抛 `NotImplementedError`。
- `upload_report` 直接抛 `NotImplementedError`。

**影响**：

- 报告任务必然失败。
- 报告页无法读取 `audit_reports`。
- DOCX 下载入口不可用。

**处置**：

- 实现 DOCX 渲染。
- 上传 MinIO。
- 写入 `audit_reports`。
- 运行时签发下载 URL。

#### P0-7 rewrite Worker task 缺失

**现象**：

网关会派发 Celery `rewrite`，Worker 只注册 `parse_doc`、`run_audit`、`gen_report`。

**影响**：

- AI 改写请求超时或返回 502/504。
- 前端 Diff 面板无法进入真实结果态。

**处置**：

- 新增 `worker/tasks/rewrite.py`。
- 包装 `ai_engine.agents.rewriter.rewrite_clause()`。
- 注册到 Celery `include`。
- 返回值按 `RewriteData` alias 输出。

#### P0-8 MinIO 文件链路不可用

**现象**：

- Compose 将 API 的 MinIO endpoint 设为 `minio:9000`。
- 预签名 URL 会带该 host 返回浏览器，浏览器无法解析。
- `contracts` bucket 实测不存在。
- 没有 bucket 初始化和明确的 CORS 配置。

**影响**：

- 浏览器直传失败。
- `/contracts/upload` 的 `stat_object` 失败。
- 报告上传和下载失败。

**处置**：

- 分离内部 endpoint 与公网 endpoint。
- 新增 `CG_MINIO_PUBLIC_ENDPOINT`。
- Compose 增加 bucket 初始化和 CORS。
- 预签名 URL 使用公网 client 签发，不能用内部 client 签完再改 host。

### 2.2 P1：影响完整体验和稳定性

| # | 问题 | 处置 |
|---|---|---|
| P1-1 | `contract_elements` 按 `ContractChunk` 存取，但前端需要 key/value/confidence/isCustom | T-D6 使用 `extra` 映射并调整投影器 |

| P1-7 | FastAPI 错误体与 OpenAPI `ApiError` 不完全一致 | 增加统一异常处理，保留 detail，并补 code/message/traceId |
| P1-8 | SSE 断线兜底只轮询一次 | 改成受控周期轮询并在终态停止 |

## 3. 目标数据流

### 3.1 推荐闭环

```text
POST /contracts/presign
  → 浏览器 PUT MinIO public presigned URL
  → POST /contracts/upload
  → 创建 contracts + audit_tasks（同一 UUID）
  → Celery parse_doc(task_id=同一 UUID)

parse_doc
  → 下载源文件
  → 解析文本 / 条款 / 要素 / 印章
  → 写 contract_elements
  → 调用 audit 核心
  → 写 audit_risks / seal_detections
  → 更新 contract.status
  → 发布 task_progress:{task_id} 终态

GET /tasks/{taskId}
  → 按 celery_task_id 读取真实 Celery 快照

GET /tasks/{taskId}/stream
  → 首包数据库/Celery 快照
  → 转发 Redis Pub/Sub progress

GET /contracts/{contractId}/elements
GET /contracts/{contractId}/risks
GET /contracts/{contractId}/conflicts
GET /contracts/{contractId}/seals
  → 从 PostgreSQL 读取真实结果

POST /report/{contractId}/generate
  → Celery gen_report
  → 渲染 DOCX
  → 上传 MinIO
  → 写 audit_reports
  → GET /report/{contractId} 返回 presigned GET URL

POST /agent/rewrite
  → Celery rewrite
  → rewrite_clause()
  → 返回 RewriteData
```

### 3.2 合同状态约定

| 阶段 | 状态 | 说明 |
|---|---|---|
| 上传建行 | `PARSING` | 解析任务已创建 |
| 解析成功、审核前 | `PENDING_REVIEW` | 要素已落库，允许重试审核 |
| 审核成功 | `IN_REVIEW` | 自动化审核结果已可读 |
| 审核降级 | `PENDING_REVIEW` | 结果可用但含 warnings，需要人工复核 |
| 解析或审核硬失败 | 保持最近稳定状态 | 任务置 `FAILED`，`error_message` 记录原因 |
| 人工提交定稿 | `FINALIZED` | 现有 commit 流程负责 |

说明：当前 OpenAPI 没有 FAILED 合同状态，因此硬失败不能伪造新枚举；通过任务终态和错误消息表达。

## 4. T-D6 局部最优方案

### 4.1 任务定位

**T-D6 解析审核桥接与前端闭环**

前置：

- T-D2 网关真实化已完成到当前工作树状态。
- T-D1 数据层和 Alembic 已落盘。

依赖建议：

```text
T-D3 报告基础设施
  → T-D6 解析审核桥接
  → T-D4 真实基础设施 E2E
  → T-D5 前端最终合并与适配
```

### 4.2 Worker 临时复用网关 DAL

**决策**：

Worker 暂时依赖 `api-gateway` workspace 包，复用：

- `app.db.models`
- `app.db.session`
- `app.db.repository.contract`
- `app.db.repository.result`

**理由**：

- 改动最小。
- 不复制 ORM 和字段定义。
- 不需要立刻迁移 `app.generated.schemas`。
- 符合演示期“局部最优”目标。

**明确技术债**：

- Worker 进程因此加载网关应用代码。
- 长期应在独立任务中抽离共享 DTO 与数据访问包。
- T-D6 不得把这个临时桥接包装成长期架构。

### 4.3 单流水线任务

`parse_doc_task` 改成一个端到端处理任务：

1. 解析源文件。
2. 把真实抽取要素写入 `contract_elements`。
3. 把印章结果写入 `seal_detections`。
4. 更新合同状态为 `PENDING_REVIEW`。
5. 调用审核核心函数。
6. 把风险和矛盾写入 `audit_risks`。
7. 成功或降级时更新合同状态为 `IN_REVIEW` 或 `PENDING_REVIEW`。
8. 返回完整结果 payload。

保留独立 `run_audit` task，但让其与 T-D6 共用同一个审核核心函数，禁止复制两套审核逻辑。

**进度映射建议**：

| 阶段 | percent |
|---|---:|
| fetch | 0.05 |
| route | 0.10 |
| parse_text | 0.28 |
| seal | 0.34 |
| extract | 0.40 |
| persist_elements | 0.45 |
| audit_classify | 0.52 |
| audit_extract | 0.60 |
| audit_risk | 0.72 |
| audit_conflict | 0.82 |
| audit_compare | 0.90 |
| audit_persist | 0.95 |
| done | 1.00 |

**失败语义**：

- 解析失败：不进入审核，任务 FAILED，合同保持 `PARSING`，写错误摘要。
- 审核硬失败：要素保留，任务 FAILED 或按约定返回结构化失败，合同保持 `PENDING_REVIEW`。
- 审核降级：任务 DONE，结果中标记 DEGRADED，合同 `PENDING_REVIEW`，前端提示需要复核。

### 4.4 抽取要素映射

现有 `contract_elements` 按 `ContractChunk` 设计，前端却需要 `ContractElement`。

**短期兼容规则**：

| ContractChunk 字段 | 映射 |
|---|---|
| `doc_id` | `contract_id` |
| `chunk_id` | `ContractChunk.make_chunk_id(contract_id, element.key, 0)` |
| `source_type` | `STANDARD_CLAUSE`，作为当前枚举约束下的兼容值 |
| `chunk_type` | `PARAGRAPH` |
| `section_id` | `element.key` |
| `section_path` | `contract_id/{element.key}` |
| `title` | `element.label` |
| `text` | `element.value`；为空时使用 label 作为占位，真实空值存 `extra` |
| `bbox` | `element.bbox` |
| `category` | `CONTRACT_ELEMENT` |
| `extra.value` | 原始 `element.value`，允许 null |
| `extra.confidence` | `element.confidence` |
| `extra.isCustom` | `element.isCustom` |

`ContractProjector.elements()` 必须从 `extra` 还原前端 DTO，不能用占位 text 冒充真实值。

**明确债务**：

当前枚举没有“合同要素”来源类型，也没有独立要素表。T-D6 采用 extra 映射只保证闭环，长期应拆分为真正的 `contract_elements` 与 `contract_chunks` 两张表。

### 4.5 任务 ID 与进度发布

**统一 ID**：

```text
gateway_task_id = uuid4()
audit_tasks.id = gateway_task_id
celery_task_id = gateway_task_id
send_task(..., task_id=gateway_task_id)
```

**状态查询**：

```python
snapshot = dispatcher.get_status(record.celery_task_id)
```

**进度发布**：

```text
task_progress:{gateway_task_id}
```

Worker reporter 应优先使用 `self.request.id`，避免依赖 contract_id 或额外参数拼 channel。

### 4.6 报告生成与下载

T-D3/T-D6 联合完成：

- `gen_report_task` 读取合同、要素、风险、矛盾和印章。
- 使用 `python-docx` 输出 DOCX。
- `upload_report` 写入 MinIO `reports/{contractId}/...`。
- 写 `audit_reports`，`format=DOCX`，`status=DONE`。
- 失败时写 FAILED 状态和错误消息，或保持可查询失败边界。
- `GET /report/{contractId}` 每次运行时签发 GET URL，不把 URL 落库。

### 4.7 Agent rewrite

新增 Worker 任务：

```text
rewrite
  → 解析 AgentRewriteRequest
  → 调用 ai_engine.agents.rewriter.rewrite_clause()
  → 返回 RewriteData alias payload
```

必须注册到 `worker.main.celery_app.include`。

### 4.8 MinIO 处理方案

**配置**：

```text
CG_MINIO_ENDPOINT=minio:9000
CG_MINIO_PUBLIC_ENDPOINT=localhost:9000
```

**实现**：

- 内部 client 用于 `stat_object`、上传报告等 SDK 操作。
- 公网 client 只用于 `presigned_put_object` 和 `presigned_get_object`。
- 两个 client 使用各自 host 分别签名，不允许 URL 字符串替换 host。

**Compose**：

- 增加 `minio-init` 服务创建 `contracts` bucket。
- 配置允许 `http://localhost:5173` 和 `http://localhost:8080` 的 CORS。
- `api` 与 `worker` 保留内部 endpoint。
- `api` 额外注入 public endpoint。

### 4.9 前端适配

| 模块 | 改动 |
|---|---|
| `client.ts` | 错误体兼容 `detail` 与 `message`，保留 traceId |
| `services.ts` | SSE 监听命名 `progress`，终态关闭，错误周期轮询 |
| `UploadPanel` | 不再把 `.local` 当作正常流程；真实上传失败必须显示 |
| `Audit` | 生成报告不立即跳转，先订阅任务并在 DONE 后加载报告 |
| `Report` | 处理尚未生成、任务失败和重新生成三类状态 |
| `Feedback` | 从 `GET /feedback` 读取真实列表，统计前端派生，导出 CSV |
| `Settings` | 保存 `enabled` 与 `reviewThresholds`，重新加载后保持 |
| `vite.config.ts` | 代理目标改为 `http://localhost:8000` |
| Docker Web | 增加 SPA fallback |

## 5. 接口与类型变更

### 5.1 OpenAPI 增量

只做加法，不破坏现有字段：

#### 新增 `GET /api/v1/feedback`

请求参数：

| 参数 | 类型 | 必填 | 说明 |

## 8. 风险与回滚

| # | 风险 | 缓解 | 回滚 |
|---|---|---|---|
| 1 | Worker 依赖 api-gateway 造成应用耦合 | 单独适配模块，禁止反向 import | 移除 workspace 依赖，恢复旧 worker 入口 |
| 2 | 单流水线任务耗时过长 | 阶段进度、超时和结果落库分开记录 | 恢复 parse_doc 和 run_audit 双任务链 |
| 3 | extra 映射被长期滥用 | 只允许 CONTRACT_ELEMENT 类记录使用 | 删除该 category 数据，恢复投影器 |
| 4 | 统一任务 ID 与旧数据冲突 | 只对新任务启用，旧任务兼容读取 | 保留旧记录，不重写历史主键 |
| 5 | 契约加法导致生成物漂移 | 只改 openapi.yaml 后 codegen | 回滚 OpenAPI 与生成物 |
| 6 | MinIO 公网地址配置错误 | 启动自检 bucket、host、CORS | 回退内部 endpoint，仅保留服务端链路测试 |
| 7 | 全局异常处理改变错误体 | 保留 `detail` 兼容字段 | 回退 middleware/handler |

**禁止事项**：

- 不手工修改 `schemas.py`、`types.ts`、`zod.ts`。
- 不新增第二套任务状态、风险枚举或文件元数据定义。
- 不在前端通过 mock 把失败任务伪装为成功。
- 不在未验证情况下把 `minio:9000` 暴露给浏览器。
- 不把 T-D6 的直接复用描述为最终架构。
