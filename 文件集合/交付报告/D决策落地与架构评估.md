**三条被实测改写的结论（必须记住）**

1. **结构化输出不能走 `json_schema`**：DeepSeek 返回 400 → 统一走 **function calling**（实测可用），适配层要留降级链。
2. **`deepseek-flash` 是 reasoning 模型**：`reasoning_tokens` 先吃 `max_tokens`，给小了 `content` 直接空串 → `max_tokens` 默认 2048 是**下限**。
3. **ollama 目前不可用（服务未启动）**：它能被配置选中，但**不能做默认值** —— 否则冒烟与测试会因连不上而红。

## 3. 文档体系升级：从两层到三层（**为了"小步 plan + 单点 goal"**）

### 3.1 为什么要升级

现状：`N-M` 任务层的粒度是「**交付批次**」（0.5~3 人日，跨多个技术点）→ 直接驱动 goal 会出现
「一个 goal 同时搞定配置、装配、算法、测试」—— 这正是你说的**工作量太大**。

升级：在任务层之下加 **组件层** `N.C<k><组件名>.md` =
**一个技术点 = 一个 goal（0.2~0.5 人日）**。

```text
模块层  N.<模块名>.md        ← 框架性总起：目标 / 架构 / **组件索引 §X.5.1** / 任务索引 / 边界
  └─ 任务层  N-M<子任务名>.md  ← 交付批次（跨组件集成验收）
       └─ 组件层  N.C<k><组件名>.md  ← 一个技术点 = 一个 goal（本组件内自证）
```

**三层不允许重复定义**：组件卡只写本组件（接口/规则/断言/回填）；
任务文档的 `§⑦` 是**跨组件集成**断言，组件卡的 `§⑦` 是**组件内单元**断言 —— 范围不同，不算重复。

### 3.2 怎么用（**plan 拆点 → goal 单点**）

```text
① Plan：读模块总纲 §X.5.1 组件索引 → 按「上游优先」排出开工顺序（就是依赖图拓扑序）
② Goal：每次只领**一张组件卡**，objective 用下面模板
③ 验收：卡内 §⑦ 断言绿 + pytest ≥ 317 passed + 卡内回填表填完 → 提交（一卡一提交）
④ 模块闭合：当某任务的所有组件卡都 ✅，跑该 `N-M` 文档的 §⑦ 做**批级**验收
```

**Goal objective 模板（组件卡版）**：

```text
目标：按《文件集合/codex/<模块>/<组件卡>.md》完成组件 C-<k>（归属 <任务 ID>）。
完成定义：① 卡内 §⑦ 断言逐条实测通过；② pytest ≥ 317 passed（命令见 AGENTS.md §4.1）；
③ 回填卡内「实测后回填」表；④ 只改卡内「落点」列出的文件。
约束：遵守卡内「适配性三问」（依赖方向 / 复用的唯一处符号 / 不许新造什么）。
停手条件：AGENTS.md §3.3。
```

### 3.3 组件覆盖率（**不制造空文档**）

- **只为"还没实现"的组件落盘卡片**：模块 1 有 5 张（切片器增量 / 向量化器 / 重排器 / Milvus 向量库 / 评测），模块 2 有 14 张。
- **已实现的组件不再单独立文**：模块 3 的 8 个组件全部已实现 → 只在 `3.OCR模块.md §3.5.1` 登记
  「落点 + 证据（测试文件 / 用例名）」；模块 1 的 C1/C6/C7/C8/C9 同理。
