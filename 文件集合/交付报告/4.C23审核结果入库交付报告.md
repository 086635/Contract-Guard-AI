## 1. 交付范围

本卡负责：

- 审核结果入库：最新 `RUN_AUDIT` 任务 DONE 后，把快照顶层的 `risks` / `conflicts` 写入 `audit_risks`。
- 在 `GET /contracts/{id}/risks`、`.../conflicts` 读前触发 `finalize_audit`（幂等）。

本卡不负责：

- 新增 API 端点、修改 `openapi.yaml` / 生成物。
- 让 worker 直连 PostgreSQL。
- 重写审核逻辑或风险/矛盾内容。
- 解析结果入库与审核派发（属上游卡 `4.C22`）。

### 背景（为什么本卡存在）

C22 补上了「解析结果入库 + `run_audit` 派发」，但审核产出的 `risks` / `conflicts` 仍没有落库路径——`RiskRepository.bulk_upsert` 此前只在测试里被调用。C23 沿用同一「gateway 按 Celery 结果惰性落库」模式补齐这一段，使 `GET risks/conflicts` 能读到真实审核结果。

## 2. 实现内容

### 2.1 `IngestionService.finalize_audit`

落点：`apps/api-gateway/app/services/ingestion.py`

流程：

1. 读取最新 `RUN_AUDIT` 任务；无任务行或 `celery_task_id` 为空直接返回 `False`。
2. 按 `celery_task_id` 读取 Celery 快照；非 DONE（RUNNING/FAILED/无快照）返回 `False`，**不写库**。
3. 只信任快照 `result` 顶层的 `risks` / `conflicts`，缺失按空列表处理。
4. `EnhancedRiskItem.model_validate` / `CrossClauseConflict.model_validate` 逐条校验；单条失败隔离为 warning。
5. `RiskRepository.bulk_upsert(contract_id, [*risks, *conflicts])` 写入并 `commit`。
6. 埋点 `log_event`（含 `trace_id` 与 `contract_id`）。

### 2.2 触发点

`ResultService.risks / conflicts` 在 `_require_contract` 之后调用 `IngestionService(self._context).finalize_audit(contract_id)`（幂等，重复读不重复写）。

### 2.3 幂等与状态边界

- 幂等：`audit_risks` 按结果主键（`id`）冲突更新，重复 `finalize_audit` 不重复建行。
- 状态边界：仅 `DONE` 且快照 `result` 非空才入库；`RUNNING` / `FAILED` / 无快照 / 无任务均不入库。
