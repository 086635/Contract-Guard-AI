## 1. 任务目标

C62 把「任务状态只活在 Redis/Celery」改成「**DB 任务行是唯一可恢复状态源**」：

1. 扩展 `audit_tasks` 的尝试/心跳/重试/终态字段，且对旧任务兼容。
2. 配置 Celery：`acks_late`、`prefetch=1`、软/硬超时、有限指数退避。
3. 任务派发前先建立可恢复任务记录，派发失败立刻置终态。
4. 保持外部 `TaskProgress/Status` 枚举兼容（不新增 QUEUED/CANCELLED）。

## 2. 实现说明

### 2.1 模型与迁移

落点：`app/db/models.py`、`alembic/versions/20261001_0012_add_task_reliability_fields.py`

```text
AuditTask += attempt_count(NOT NULL, default 0) | max_attempts(NOT NULL, default 3)
             last_heartbeat_at | next_retry_at | error_code | locked_at | completed_at  (均可空)
```

**迁移用「便携式重建」而不是 `ALTER TABLE`**（同文件已注释理由）：

1. 除加列外还要**放宽 `audit_task_type` CHECK**（新增 `REWRITE`/`SCAN_UPLOAD`/`CONVERT_DOC`）
   并放宽列宽 `VARCHAR(10) → VARCHAR(11)`（`SCAN_UPLOAD`/`CONVERT_DOC` 有 11 个字符）；
2. 该 CHECK 是 `CREATE TABLE` 内联的，SQLite 与「离线迁移守卫（把 PG DDL 灌进 SQLite）」都不支持 `DROP CONSTRAINT`；
3. `RENAME → CREATE → INSERT SELECT → DROP` 在 PostgreSQL 与 SQLite 上都是合法 SQL，
   因此离线守卫（逐列比对 `Base.metadata`）与真实 PG `upgrade/downgrade` 都能覆盖。

> ⚠️ **本轮顺带修掉一个既有缺陷**：C57 的 `SCAN_UPLOAD`、C59 的 `CONVERT_DOC` 任务行
> 原先会被 CHECK 拒绝（且 11 字符超过 `VARCHAR(10)`），即「扫描/转换任务在生产 DB 里根本落不了库」。
> 本次迁移把类型白名单一次性补齐。

### 2.2 仓储：可恢复 + 终态

落点：`app/db/repository/contract.py`

```text
TaskRecord   += 7 个可靠性字段
             + can_retry           （attempt_count < max(1, max_attempts) 且非 DONE）
             + retry_delay_seconds （base ×2^(已完成尝试-1)，封顶 300s）  ← 重试策略唯一定义处
TaskRepository.create(..., max_attempts=3)   # 派发前调用（celery id 可为 None）
TaskRepository.attach_celery_task_id(...)    # 派发成功后回填
TaskRepository.mark_failed(..., error_code)  # 终态 + errorCode + completedAt
```

### 2.3 派发顺序（`ContractService.upload`）

```text
① 先写任务行（celery_task_id=None, attempt_count=0, max_attempts=3）
② 派发 Celery：失败 → mark_failed(error_code="DISPATCH_FAILED") 并提交后抛出
③ 成功 → attach_celery_task_id() 后提交
```

旧实现是「先派发、再写行」，进程在中途挂掉就会留下**跑着但库里没有**的任务；现在反过来，
即使进程崩溃，也留下一条可被 C63 reconciler 对账的 `RUNNING` 行。

### 2.4 Celery 可靠性配置（`worker/main.py`）

```text
task_acks_late = True                    # 先执行后确认，崩溃不丢任务
task_reject_on_worker_lost = True        # worker 被杀也重投，不留永久 RUNNING
worker_prefetch_multiplier = 1           # 已存在，保持
task_soft_time_limit = 600 (CG_TASK_SOFT_TIME_LIMIT)
task_time_limit     = 900 (CG_TASK_TIME_LIMIT)
task_default_retry_delay = backoff_max / max_retries
task_annotations = {parse_doc|scan_upload|convert_doc:
    autoretry_for=(OSError, TimeoutError), max_retries=3,
    retry_backoff=True, retry_backoff_max=300, retry_jitter=True}
```

- **分类重试**：只对瞬时/基础设施异常（`OSError`/`TimeoutError`）自动重试，**不吞编程错误**（§⑨-2）。
- **有限重试**：`max_retries=3`（Celery 侧）+ `max_attempts`（DB 侧，重试上限的唯一判据）。
- **只对可重放任务开放**：`parse_doc` / `scan_upload` / `convert_doc`（⑥-2）。
- `convert_doc` 的 `convert` 队列路由保持不变（C59 不受影响）。

## 7. 边界与后续

### 边界声明

- **不新增 QUEUED/CANCELLED 到外部枚举**：阶段仍用 `stage` 表达（`queued`/`running`…），`Status` 保持三态；
- **不无限重试**：`max_retries`（Celery）+ `max_attempts`（DB）双重上限；
- **不让 Redis 成为唯一状态源**：任务身份/尝试/终态都落 `audit_tasks`，Redis 只做进度与队列；
- **不新增第二套任务状态表**：字段加在既有 `audit_tasks` 上。

### 三处需知晓的决策

1. **迁移用重建而非 ALTER**：见 §2.1（内联 CHECK 无法在 SQLite 侧 DROP；离线迁移守卫会把 PG DDL 灌进 SQLite）。
2. **重试策略的唯一定义处在 DB 行上**（`TaskRecord.can_retry` / `retry_delay_seconds`）：因为
   `worker` 不能 import `app`，且 ② 明确「DB 任务行是状态源」；Celery 注解只负责传输层重投。
3. **改了一个既有测试夹具**：`test_sse_e2e._record()` 补 `attempt_count/max_attempts`。
   该夹具模拟「已落库的任务行」，而新列在库中 NOT NULL；**未改任何断言**，只让夹具与库表一致。

### 未做（明确归属）

- **心跳写入 / stale 回收 / 重试调度**：`last_heartbeat_at`/`next_retry_at`/`locked_at` 已就位，
  但写入与扫描属 **C63**（`4.C63Stale任务回收与心跳对账.md`）；
- **SSE stream token**（60s、单任务范围）：**C64**；
- **转换/扫描任务的审计回写**（C57/C59 遗留）：与 C63 的 reconciler 一起落地（C63 明确「标记 FAILED 并写审计」）。

### 后续

- **C63**：reconciler + 心跳 + stale 回收（消费本卡的 `can_retry` / `retry_delay_seconds` / `max_attempts`）。
- **C64/C65**：SSE stream token 与前端令牌/断线轮询。
