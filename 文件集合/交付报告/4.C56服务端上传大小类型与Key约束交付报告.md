## 1. 任务目标

C56 把上传准入从「前端体验校验」改成「服务端安全边界」（对应 D7-I13 的解决路径第 1~2 层）：

1. `PresignRequest` 兼容新增 `sizeBytes` / `contentType`（**只做加法**，不改既有字段）。
2. 服务端在 presign 阶段拒绝超限 / 类型不符 / 扩展名与声明不一致。
3. 文件 key 只能由服务端生成；客户端回传任意 key 一律拒绝，且**不得触碰对象存储**。
4. upload 阶段重新 `stat_object` 复核大小与 ETag。

## 2. 实现说明

### 2.1 契约（唯一 SSOT）

落点：`packages/schema/openapi.yaml`（+7 行，纯加法）

```text
PresignData        += contentType?(string)
/contracts/presign += sizeBytes?(integer, minimum 1) / contentType?(string)
UploadBody         += sizeBytes?(integer, minimum 0) / etag?(string)
/contracts/upload  += 413 FileTooLarge / 415 UnsupportedType 响应声明
```

> 注意：**没有**在契约里对 `sizeBytes` 设 `maximum: 52428800`——若设成 schema 约束，FastAPI 会先返回 422，与「超限 → 413 `ERR_FILE_TOO_LARGE`」的既有错误语义冲突。上限由服务层唯一常量 `MAX_UPLOAD_BYTES` 承担。
> 生成物 `app/generated/schemas.py`、`src/api/generated/{types,zod}.ts` 由 `tsx scripts/gen-*.ts` 重新生成，**未手改**（三者在 `.gitignore` 中，不入库）。

### 2.2 服务端准入

落点：`apps/api-gateway/app/services/contract_service.py`

```text
MAX_UPLOAD_BYTES = 50 * 1024 * 1024          # 唯一处
_ALLOWED_EXTENSIONS = {PDF_NATIVE/PDF_SCANNED -> .pdf, DOCX -> .docx}
presign: 扩展名↔类型不符/未开放类型 -> 415；超限 -> 413；production 缺 sizeBytes -> 400
upload : 先 validate_upload_object(key) 再 stat_object，最后复核 size/etag/max_bytes
```

### 2.3 对象复核 helper

落点：`apps/api-gateway/app/services/storage.py`

```text
validate_upload_object(file_key, info=None, *, expected_size, expected_etag, max_bytes)
UploadObjectError(status_code, detail)   # detail 为安全摘要，不回显文件内容
_UPLOAD_KEY_RE = ^contracts/\d{4}/\d{2}/[0-9a-f]{32}-[^/\\]+$
```

`info=None` 时只复核 key 形态，供「stat 之前」调用——非法 key 不触发 bucket 访问。

### 2.4 路由错误映射

落点：`apps/api-gateway/app/api/v1/contracts.py`

`presign` / `upload` 捕获 `UploadObjectError` → `HTTPException(status_code, detail)`。经既有全局错误包络（C51）输出 `ApiError{code:ERR_FILE_TOO_LARGE|ERR_UNSUPPORTED_FILE_TYPE|ERR_DATA_CONFLICT|ERR_VALIDATION}`。

### 2.5 前端（只作提示层）

落点：`apps/web-ui/src/api/services.ts`、`apps/web-ui/src/components/contracts/UploadPanel.tsx`

- `presign(fileName, fileType, sizeBytes, contentType)` 提交声明值；
- `directUpload` 返回 MinIO PUT 的 `ETag`（读不到则为 `null`）；
- `submit` 带上 `sizeBytes` 与（可选的）`etag`，服务端复核后才建合同。
- `chooseFile` 仍保留「>50 MB / 非 pdf,docx 直接拦」的前端提示（未删弱化）——前端只作提示，不承担安全。

## 6. 边界与后续

### 边界声明

- 未改 `rag_contracts`；未改 `rag_core/service.py`；未新增第二套上传路由或 key 规则；
- 未把扩展名/Content-Type 当内容判据——真实内容判据留给 **C57** 的 magic sniff；
- 未信任客户端：`sizeBytes/etag/contentType` 全部在服务端与 `stat_object` 复核；
- 未放宽既有断言，未改动既有错误码枚举。

### 已知限制（交 C57 与部署卡）

1. `FileType.IMAGE` 目前**未开放**（`_ALLOWED_EXTENSIONS` 无该项 → 415）。母文档 §⑤.8 的「约定图片类型」需先由卡片定义允许集合，故本轮不放行。
2. 浏览器能否读到 PUT 响应的 `ETag` 取决于对象存储 CORS 是否暴露该响应头；当前 `docker/minio-cors.json` 只配 `MINIO_API_CORS_ALLOW_ORIGIN`，为此 `etag` 在服务端是**可选**校验项（客户端拿不到就不比对）。

### 后续

- **C57**：`scan_upload` 任务做 magic sniff + PDF/DOCX 结构校验 + ClamAV 扫描；扫描不通过不得派发 parse。
- **C58/C67**：预览与生产 profile 会消费同一 `ObjectStoragePort` 与对象 key 规则。
